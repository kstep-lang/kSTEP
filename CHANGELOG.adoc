= Changelog
:toc:

All notable changes to kSTEP are documented here. The project follows
https://semver.org[Semantic Versioning]; while the major version is `0`, the API is unstable and
minor versions may contain breaking changes.

== Unreleased

=== Added

* kSTEP Desktop export dialog (Welle D7, ADR-0057): toolbar `Export...` or Cmd/Ctrl+E writes the open script as STEP AP242, GLB, STL
  or 3MF. Format first, then the target; the export runs on the saved file (`Save and Export` or `Export Saved Version` with unsaved
  changes). The script runs only in a supervised worker (new `DesktopExportWorker` with a strict argument whitelist and its own
  orphan watchdog, so a 120 s export is not halted at 70 s). The worker output goes to a private session directory, is validated
  (size cap 512 MiB, magic bytes) and moved to the target atomically, with no non-atomic fallback; links and non-regular targets are
  refused, an existing file is replaced only after an inline `Replace` confirmation. A structure-only script exports as STEP; STEP
  with shapes but without OCCT is refused instead of silently writing structure only. `Stop` (Esc or Cmd/Ctrl+.) kills the worker
  and writes nothing. New error codes `KSTEP-D-019` to `KSTEP-D-024`. No new dependency; `runExport` in kstep-cli is now `internal`.
* kSTEP Desktop AI panel (Welle D6a, ADR-0056): describe a change in words and get a proposal as a diff. A new unpublished module
  `kstep-desktop-ai` (Koog as a minimal Anthropic client behind a hardened transport; no tools, no agent). The panel (toolbar `AI`
  or Cmd/Ctrl+K) shows a prompt field, an optional "Include current script" tick, `Generate`/`Stop`, up to 4 attempts, and the
  proposal as a diff with `Apply` (one undo step, nothing saved, never run by itself) and `Discard`. Each candidate is first compiled
  in the same supervised worker as the live preview; compile errors go back to the model (scrubbed of paths and key-like strings).
  Limits: 4 attempts, 180 s in total, 60 s per call, 200 KiB response, 1 MiB script, 4,000-character prompt, 8,192 output tokens.
  Nothing is sent before an explicit consent per provider and host. The API key comes from the system keychain (macOS Keychain, Linux
  Secret Service), this session only, or `KSTEP_AI_ANTHROPIC_KEY`; it is never written to a file or logged. New error codes
  `KSTEP-D-014` to `KSTEP-D-018`. The CLI zip stays free of the AI client (new `verify-dist` guard). Anthropic only; the generated
  script is run on this computer to check it and the worker is not a sandbox (see the ADR).
* kSTEP Desktop transparency (Welle D5, ADR-0055): make a part or a whole sub-assembly transparent or hidden. An eye column in the
  assembly tree (click: visible, transparent, hidden; a group shows a mixed state), toolbar controls `Show all`, `Isolate`, `Hide` and
  an opacity slider (5 % to 60 %, default 25 %), and the keys `T` (transparent), `V` (hide), `I` (isolate), `Shift+V` (show all) and
  Space in the tree. Hidden parts are not drawn and not picked; a click picks the nearest opaque part, a transparent one only when
  nothing opaque is hit. Visibility survives a re-run of the same file and resets for another file; `H` still resets the camera. The
  STEP colour transparency is still not drawn in the desktop. Additive API: `CanvasVisibility`, the `visibility` parameter of
  `ShapeCanvas`, `PickIndex.pick(ray, mode)`. No new dependency.
* kSTEP Desktop assembly tree (Welle D4, ADR-0054): a tree of the assembly beside the canvas. Click a part or a whole sub-assembly to
  select it (the group tints all its parts and the inspection panel shows its part count, triangles, size and centre), hover a row to
  highlight it, open and close groups with the triangle or the keyboard (Up/Down, Left/Right, Home/End, Enter, Escape), toggle it with
  `Tree` in the toolbar. The render worker reports the hierarchy as a `tree` next to the part list and the desktop validates it; an
  untrustworthy tree is not shown and gives the warning `KSTEP-D-013` while click selection keeps working. `kstep render --output json`
  is unchanged (the tree is a desktop-worker extra). Additive API: `PreviewOutcome.Rendered.tree`, `RenderedAssemblyTree`,
  `RenderedTreeNode`, `CanvasHighlight.selectedLast`/`hoveredLast`. No new dependency.
* kSTEP Desktop selection and inspection (Welle D3, ADR-0053): hover tints the part under the pointer, a click selects it (a click on
  empty space or Escape clears), and an inspection panel shows its name, triangle count, size, centroid, colour and position. The render
  worker now reports the drawn parts and the desktop validates the list against the GLB; an untrustworthy list switches selection off
  with the warning `KSTEP-D-012`. No new dependency; `kstep render --output json` is unchanged (the part list is a desktop-worker extra).
  Additive API: `ProjectedTriangle.sourceIndex`, `MeshProjection.projectFramed`, `GlbWriteResult.keptSourceTriangles`.
* kSTEP Desktop script editor (Welle D2, ADR-0052): the window shows an editor next to the preview. Kotlin syntax colouring with the
  kSTEP DSL names, a gutter with line numbers and error/warning marks (hollow while the buffer has unsaved changes), click on an error
  to jump to its position, explicit save (Cmd/Ctrl+S) by temp file, `fsync` and atomic rename, own undo/redo, indentation on Enter and
  Tab as four spaces. A file that changes on disk reloads a clean buffer and shows a Reload / Keep mine banner for a dirty one;
  closing or opening with unsaved changes asks Save / Don't Save / Cancel. Files over 1 MiB, not UTF-8 text or with a line over 20 000
  characters stay preview-only. New codes `KSTEP-D-009` to `-011`. No new dependency; still one watcher and one run path.
* Opt-in native runtime archive (Welle D0a, ADR-0050): `:kstep-cli:nativeRuntimeZip` builds
  `kstep-<version>-<platform>-native.zip` for the host platform (CLI, `bin/kstep` launcher, OCCT and PlaneGCS bridges as plain
  files under `lib/native/<platform>/`; OCCT itself is not bundled). New `kstep.native.embedInJar` Gradle property and
  `scripts/release/verify-native-dist.sh`. Not part of the release pipeline.
* `kstep --version` prints the version (in the native archive also the bridge status) and an OCCT install hint is printed
  when the native archive cannot load OCCT.
* `kstep render -f stl` and `-f 3mf` (Welle AB, ADR-0049): binary STL and 3MF mesh export in millimetres. STL is one merged
  mesh and drops colours explicitly (warning); 3MF keeps colours (alpha as `#RRGGBBAA`), one object per distinct part and one
  build item with a transform per placed instance. No geometry means exit 1 and no file (never a text card inside a printer file).
* `--tolerance <mm>` (stl/3mf): absolute chordal deviation, never finer than bounding-box diagonal / 2000.
* `--require-watertight` (stl/3mf): fail, writing nothing, if a part mesh is not closed and consistently oriented under 1e-6 mm
  welding. Without the flag a non-watertight mesh is written with a warning. `--output json` gains a `meshExport` object.
* `kstep-desktop` (Welle D1, ADR-0051): live preview of a `*.kstep.kts` script (`./gradlew :kstep-desktop:run`), re-rendered on
  save in a supervised worker subprocess (new `dev.kstep.cli.DesktopRenderWorker`; timeout, heap and output limits, orphan halt). GLB
  read-back (`GlbMeshReader`), polling file watcher, generation-based cancellation, last good result with badge, error bar with the
  new codes `KSTEP-D-001` to `-008`. Not published and not part of the CLI zip (`verify-dist.sh` now fails if desktop, viewer or
  Compose jars appear in it).

=== Changed

* The kSTEP Desktop render workers (live preview and AI candidate check) no longer inherit secret-like environment variables
  (`KSTEP_AI_*`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `*_API_KEY`, `*_TOKEN`, `*_SECRET*`, `*PASSWORD*`), so a script cannot read
  them (ADR-0056).

* `ShapeCanvas` gains an optional `fitReference` parameter (behaviour unchanged without it); `UnavailableNotice` gains `installHint`.
* `ImportWorkerSupervisor` (new optional `onStarted` callback), `ImportWorkerLaunch.command` (`classPath`, `extraJvmOptions`),
  `WorkerTempDir`, `WorkerOutcome` and `diagnosticLine` of the unpublished `kstep-cli` are now public so `kstep-desktop` can use them.
* The native bridge gains `nativeShapeTrianglesWithTolerance` (bounded tolerance entry point); the default tessellation is
  unchanged. The native library must be rebuilt (the Gradle build does it).

=== Fixed

* The OCCT install hint of `kstep-viewer` showed the apt command on every operating system; on macOS it now shows Homebrew and the
  native archive.

== 0.5.0 — 2026-11-17 (pre-release)

=== Fixed

* A STEP file whose `SURFACE_STYLE_TRANSPARENT` value is not a finite number in 0..1 is now refused before OCCT reads it
  (`limit:` error, `LIMIT_EXCEEDED`). OCCT 7.9.2 (Ubuntu 26.04) aborts the whole process with a stack-smashing error on such a
  value; found when the hostile-alpha tests of Welle Y crashed the Linux CI job. Reproduced and verified in an x86-64 Ubuntu 26.04 container.

=== Documented

* Path-exact colours through `SPECIFIED_HIGHER_USAGE_OCCURRENCE` (ADR-0048, Welle AA): the gate failed. OCCT 7.9.3's XCAF reader
  (SHUO mode on) delivers the colour to exactly one path, but OCCT's own presentation logic ignores it, so nothing was built; export
  and import behave as before. The result is pinned by `PathColourOcctGateTest` and `scripts/interop/verify-path-colour-gate.sh`.
  ADR-0030 is corrected: SHUOs are ignored and not counted.
* Layers on assembly usages (ADR-0047, Welle Z): the gate failed. With OCCT 7.9.3 no schema-valid `PRESENTATION_LAYER_ASSIGNMENT`
  pattern reaches one placed occurrence, a layer on the solids lands on the shared part. Nothing was built; export and import
  behave as before. The result is pinned by `InstanceLayerOcctGateTest` and `scripts/interop/verify-instance-layer-gate.sh`.

=== Changed

* `styleInstance` no longer refuses alpha below 1 (it was `KSTEP-S-012`); an alpha outside 0..1 or not finite still is.
* Part colours with alpha are now drawn translucent in `kstep render` (they were drawn opaque, ADR-0042); part and instance colours share the render path.
* `MeshColor` has a fourth component `a` (default 1.0): source compatible, but the public constructor, `copy` and `component4` change (binary break).

=== Added

* Transparent instance colours (amendment of ADR-0044, Welle Y): `styleInstance(usage, colour)` accepts a colour with alpha below 1
  (also on sub-assembly occurrences). The translucent chain `SURFACE_STYLE_RENDERING_WITH_PROPERTIES` plus `SURFACE_STYLE_TRANSPARENT`
  (`t = 1 - alpha`) is written only for those colours, so every opaque export stays byte-identical and the prefix chain holds. Verified
  with OCCT's XCAF reader and presentation logic (`scripts/interop/verify-export-instance-transparency.sh`, scenarios Y0-Y8, CI test
  `InstanceTransparencyOcctGateTest`) and FreeCAD (geometry). `kstep import` reports the alpha of instance colours as before
  (`alpha` in JSON, ` alpha 0.5` in the text); hostile transparencies never leave 0..1.
* Opacity in `kstep render`: SVG gets the element `opacity` on translucent polygons, PNG blends them, GLB writes `COLOR_0` as `VEC4` and
  `alphaMode BLEND` when some triangle is translucent. Opaque renders are byte-identical. Opacity is drawn by `kstep render` only, not
  in the desktop viewer (`kstep-viewer`), and penetrating translucent parts can show painter artefacts.

* Instance colours on occurrences of sub-assemblies (ADR-0046, Welle X): `styleInstance(usage, colour)` also accepts a usage
  whose child has no shape of its own, when shapes sit below it. The colour reaches every part below that occurrence;
  the entities go into a second block behind the block of the parts (a file without sub-assembly colours is a byte prefix
  of the file with them, all existing exports stay byte-identical), with its own allow-list, a cap of 65 536 styled items
  and a self-check. A sub-assembly without any shape below it stays refused (`KSTEP-S-008`). Verified with OCCT's XCAF reader
  and presentation logic (`scripts/interop/verify-export-subassembly-colours.sh`, scenarios H0-H8, CI test
  `SubassemblyColourOcctGateTest`) and FreeCAD (geometry).

* Instance colours (ADR-0044, Welle V): one placed occurrence of a part can have its own colour, so a part used twice can be
  red once and blue once. `styleInstance(usage, colour)` in the script (opaque colours only in this wave, translucent since Welle Y; `KSTEP-S-012` for a
  translucent one in this wave, `KSTEP-S-014` for a second colour on the same usage), `UsageStyle` and a `usageStyles` parameter of
  `Ap242ShapeExporter.export`. The entities (`PRESENTATION_STYLE_BY_CONTEXT` on a one-item representation tied to the usage) are
  written behind every other entity, so a file without instance colours is a byte prefix of the same file with them and all
  existing exports stay byte-identical. A usage whose child is a sub-assembly was refused in this wave (accepted since ADR-0046). Verified with OCCT's
  XCAF reader (`scripts/interop/verify-export-instance-colours.sh`, gate scenarios G1-G8), `kstep import` and FreeCAD
  (geometry; headless FreeCAD reads no colours).
* Effective colour per occurrence (ADR-0045, Welle W): `kstep import` reports `occurrences[].colour` (instance colour of the
  last component over the whole-part colour, `null` without a colour; always present in the JSON) and appends
  `colour (r, g, b)` to the occurrence line of the text report only when there is one, so the report of a file without
  colours is unchanged. Per-face colours do not flow in (colours on sub-assembly components do, since ADR-0046).
* `kstep render` draws instance colours (ADR-0045): a part used twice can be red once and blue once in SVG, PNG and GLB.
  The instance colour wins over the part colour; instances without a colour stay neutral next to coloured ones; a script
  without `styleInstance` renders as before. Opacity was added to the render in Welle Y (see below).
* `kstep import` reports instance colours: `components[].colour` in the JSON (always present, `null` without a colour) and
  `colour (r, g, b)` on the component line of the text report.

=== Changed

* The effective colour of an occurrence (`occurrences[].colour` in `kstep import`, and in `kstep render`) now takes colours of
  outer sub-assembly components into account: own component, then part colour, then outer components, innermost first
  (ADR-0046; ADR-0045 D2 ignored them). Files from other tools with colours on sub-assembly components change their
  `occurrences[].colour` accordingly.
* `PlacedInstance` has a new last constructor parameter `usagePath` (default empty): source compatible, a binary change for
  callers of the public constructor.
* `presentation.instanceStylesIgnored` now counts only what is still not read (a layer or a curve-only colour on an
  assembly component); surface colours on instances are reported. `presentation.coloredTargets` counts instance colours too.
  The text report of a file without instance colours is unchanged.

== 0.4.0 — 2026-11-12 (pre-release)

Fifth pre-release. It adds three more face-based shape operations (pocket or hole from a face, draft, thickening),
persistent names for the inner wall of an INWARD shell, transparency and edge colours in the STEP export and import, and
a hardened `kstep import` worker. Release 0.4.0 is the first release published to Maven Central (group `dev.kstep`,
twelve library modules); the jars contain no native libraries. As before, the GitHub release carries a
platform-independent JVM-only `kstep-cli-0.4.0.zip` (about 87 MB because it bundles the Kotlin compiler for
`*.kstep.kts` scripts) and a SHA-256 checksum; nothing is published to Homebrew.

**Geometry, sketches and `kstep import` need the native bridges.** Neither the zip nor the Maven Central jars contain
them, so those features report a clear "unavailable" error there; build the bridges from source with a system
OpenCascade (Linux x86-64, or macOS arm64 via Homebrew) to use them. Interoperability is verified with
OpenCascade-based readers (OpenCascade's own readers and FreeCAD), not yet with other CAD/PLM systems.

=== Added

* Maven Central publishing (ADR-0043): the twelve library modules `kstep-core`, `kstep-express`, `kstep-step21`,
  `kstep-script`, `kstep-shape`, `kstep-geometry`, `kstep-constraints`, `kstep-sketch`, `kstep-render`, `kstep-preview`,
  `kstep-mcp` and `kstep-asciidoc` are published as `dev.kstep:<module>`, signed, with sources jars and an empty javadoc
  jar. The jars contain no native libraries: `kstep-geometry` and `kstep-constraints` ship only the Kotlin API, and users
  build the bridges themselves and load them with `-Dkstep.occt.bridge.library` / `-Dkstep.planegcs.bridge.library` (absolute paths); the jars target JDK 21.
  `kstep-cli`, `kstep-viewer` and `kstep-tests` are not published. The release workflow gets a `maven-central` job that
  runs after the GitHub release, gated on four secrets and on the tag still pointing at the built commit, and idempotent
  (all twelve POMs are probed; a partial state fails closed). An allow-list (`publishedModules`) with the coverage check
  `verifyPublicationCoverage`, the fail-closed task `verifyNoNativeLibraries` and the release scripts
  `check-maven-central.sh`, `verify-maven-artifacts.sh` and `published-artifacts.txt`; `ci.yml` stages and verifies the
  Maven repository on every PR.
* Welle Q2 (ADR-0040): faces as the input of three more operations. `pocket(shape, face, profile, depth)` cuts a
  rectangle, circle or polygon (`PocketProfile`) into the one planar face a selector names, blind or through
  (`PocketDepth`); a hole is a circular pocket. A blind depth that would reach through the material under the profile
  (stepped body, existing cavity) is refused. The profile lives in a local coordinate system of the face (origin =
  centroid, `U` = +X projected into the face, `V` = N x U) and must lie strictly inside the face; an ambiguous
  selection is `KSTEP-S-011`, not a silent first pick. `draft(shape, faces, angleDegrees, NeutralPlane(origin,
  pullDirection))` tapers planar faces (`BRepOffsetAPI_DraftAngle`; a positive angle narrows the material along the pull
  direction). `thicken(shape, faces, distance)` pushes planar faces outward and extends their neighbours
  (`BRepOffset_MakeOffset`). Matching `OcctKernel` functions and the feature types `PocketFeature`, `DraftFeature` and
  `ThickenFeature`, which rebuild with undo/redo. A tracked edge is followed through a pocket; draft and thicken report
  no usable edge history, so tracking through them is refused with the reason.
* `scripts/interop/verify-face-ops-2.sh` (with `--spike` and `--baseline`) re-checks the six example exports with OCCT and
  FreeCAD and compares the pre-Q2 examples byte for byte with the previous commit.
* Welle T (ADR-0041): persistent names for the inner wall of an INWARD shell. New sources `ShellInnerEdges(selector)` and
  `ShellInnerFaces(selector)` with the new role `GeneratedRole.CAVITY` (appended at the end of the enum): the inner copy of
  the input edge, or the edges of the inner copy of the input face, that the selector names on the shell's INPUT. A
  `ShellFeature` with direction INWARD is now a generator for `GeneratedEdges`; `OcctKernel.shellNamed` and the JNI entry
  `nativeShellShapeNamed` read edge history and generation map from the same `MakeThickSolid` maker. Strict: an input edge
  that borders only opened faces, an opened face, an ambiguous or missing image ends in an `EdgeNamingException` with the
  candidates (`KSTEP-S-011`). An OUTWARD shell cannot name its inner wall (the generated copies are the new outer skin) and
  is refused before any native call. Unnamed shells are unchanged. Example: rounding the four inner vertical edges of a
  40x30x20 box shelled with a 2 mm wall gives V = 7167.451 and 15 faces, 9816.035 after the box becomes 30 high.
  `scripts/interop/verify-shell-inner-naming.sh` (with `--spike`) re-checks the exports with OCCT and FreeCAD.
  Source-incompatible for exhaustive `when` over `GeneratedRole` or `DerivedGenerationSource` in third-party code.
* Welle U (ADR-0042): transparency and edge colours in the STEP export. `StepColour` gets an opacity: `StepColour.rgba(r, g,
  b, a)`, `StepColour.hex("#RRGGBBAA")`, `StepColour.a` and `isOpaque`; an alpha outside 0..1 or not a number is
  `KSTEP-S-012`. A translucent part or face colour is written with `SURFACE_STYLE_TRANSPARENT(1 - a)` and read back by OCCT
  and by `kstep import`. New `styleEdges(pd, edgeSelector, colour, expected)` colours single edges (`CURVE_STYLE`, opaque
  only: a translucent edge colour is `KSTEP-S-012`; no match or wrong count `KSTEP-S-011`, a second colour `KSTEP-S-014`),
  with the types `EdgeStyle` and `ShapeStyle.edges`. `kstep import` reports `alpha` in every colour object (JSON; text only
  below 1.0), a new `edgeStyles` list per part and `edge N  colour (r, g, b)` lines. The writer entry `nativeWriteStepStyled`
  has two more arguments (edge indices and colours) and four-value colours; the allow-list of the style merge gets
  `SURFACE_STYLE_RENDERING_WITH_PROPERTIES`, `SURFACE_STYLE_TRANSPARENT`, `CURVE_STYLE` and
  `DRAUGHTING_PRE_DEFINED_CURVE_FONT`, with curve styles allowed only on edges and surface styles only on solids and faces.
  An opaque colour is written by the unchanged code path, so every file without transparency stays byte-identical
  (`StepColour.rgba(1.0, 0.5, 0.0, 1.0)` equals the existing golden). `scripts/interop/verify-export-alpha-edge-instance.sh`
  (with `--spike`) re-checks the exports with OCCT and FreeCAD.

=== Changed

* Behaviour change for foreign files read with `kstep import` (Welle U, ADR-0042): a `ColorCurv` on an edge is now reported
  as an edge style instead of being counted as `presentation.unattached`; `presentation.coloredTargets` counts it. The
  JSON colour object always has an `alpha` key and every part an `edgeStyles` list (additive keys, there is no format
  version field). Text output of files without transparency or edge colours is unchanged. `StepColour.hex("#RRGGBBAA")`
  is no longer an error; the earlier "transparency is not supported" entries of Welle S below remain as history.
* `kstep import` (Welle R2, ADR-0038): the bound on the worker's stdout is 16 MiB instead of 64 MiB (the largest
  measured report at the expansion limit is about 7.5 MB).
* `scripts/release/verify-dist.sh` also imports the exported file and expects the one-line `geometry_unavailable` JSON
  error of the native-free zip.
* Documented (ADR-0038): `/dev/fd/N`, `/dev/stdin` and `/proc/self/...` are not resolved; the input must be a regular
  file, and the structured error is `KSTEP-I-003` or `KSTEP-I-004`.

=== Fixed

* `kstep import` (Welle R2, ADR-0038): the worker now runs with its own private `java.io.tmpdir` (`kstep-import-*`,
  mode 0700), which the supervisor removes after the worker is gone on every path (timeout, crash, output overflow, SIGTERM). Before, the
  extracted native bridge was left in the system temp directory whenever the worker was killed.
* `kstep import`: the stderr diagnostic line of an abnormal worker end shows the exception or error instead of the
  first SLF4J INFO line ("OCCT JNI bridge loaded ..."); log-only output prints no misleading line.
* `kstep import`: an incomplete worker output (a descendant holding the pipe) no longer uses exit value `-1`, which could
  collide with a real exit value; it is a distinct outcome and still ends as `read_failed`.
* Test suite: the worker supervisor tests no longer depend on sleeping forever or on fixed waits (stand-ins end
  themselves, process death is polled, the PID file is written atomically); the integration test replaces its
  process-list search (racy, and passing when the worker was never started) by a check of the run's temp directory, and
  honours `-Pkstep.occt.require=true`.
* Tests: the wall-clock bound of the `MeshProjection` performance test was relaxed for the slower macOS CI runner; it
  still guards against a super-linear blow-up.

=== Notes

* Not included: PMI (`kstep import` counts it and reports it as ignored, `kstep export` writes none); colours and layers
  on assembly instances (measured in ADR-0042, planned as Welle V); the opacity in `kstep render` (GLB, SVG and PNG
  ignore alpha) and face colours in the preview; layers and widths on edges; names for the inner wall of an OUTWARD
  shell (its generated copies are the new outer skin); names for pocket walls and drafted or offset faces, rotated or
  open pockets, pockets on curved faces, draft of non-planar faces and negative thickening (ADR-0040; no new native
  toolkit, `BRepFeat_MakePrism` is not used).
* Maven Central: the jars carry no OCCT or PlaneGCS library and there are no platform jars with natives; the bridges
  are built locally (see `docs/building.adoc`). `kstep-mcp` is published as a library although it has a `main()` and a
  `slf4j-simple` runtime dependency (open question in ADR-0043).
* Platforms: the native bridges are built and tested on Linux x86-64 and macOS arm64 only. Windows and Intel Macs are
  not supported and not tested (the bridges report `Unavailable` there); the JVM-only zip has not been tried on Windows.
* Interoperability: exports and imports are checked with OpenCascade-based readers only (OCCT's typed and XCAF readers,
  FreeCAD on OCCT). FreeCAD's headless reader does not read colours, so colours, transparency and edge colours were
  checked with kSTEP and OCCT; FreeCAD was used for geometry. Other CAD/PLM systems and a lossless write-back round
  trip are unverified.
* Import bounds: only the `kstep import` command runs the reader in a supervised worker process with a time and memory
  bound. Library callers of `StepImporter` / `OcctKernel.readStep` still run in-process without such a bound, and
  `kstep-mcp` has no import tool.
* Gate (2026-11-12, macOS arm64, OCCT 7.9.3): `clean check -Pkstep.occt.require=true -Pkstep.planegcs.require=true
  --no-build-cache`, 2255 tests, 0 failures, 0 errors, 18 skipped (16 "native bridge unavailable" negative tests, two
  gltf-validator tests); release-style build without natives: `verify-dist.sh` green, import, sketch solving
  (`KSTEP-S-009`) and geometry export report the bridge as unavailable, `kstep mcp` reports version 0.4.0; the Maven
  staging repository passes `verify-maven-artifacts.sh` (12 artifacts, no native libraries).

== 0.3.0 — 2026-10-24 (pre-release)

Fourth pre-release. It makes the geometry layer parametric and adds presentation data: sketches gain radius,
tangency and angle constraints and re-solve inside a feature history, edges generated by extrude, revolve, fillet,
chamfer, boolean and hole operations get persistent names, a feature history gets undo/redo, `kstep render` / preview /
GLB honour assembly placements, the OCCT bridge gains mirror, uniform scale, face and vertex selection and shell, and
colours and layers are written by `kstep export` and read back by `kstep import`, which now also reports the length
unit and runs in a supervised worker process. As before, the GitHub release carries a platform-independent JVM-only
`kstep-cli-0.3.0.zip` (about 87 MB because it bundles the Kotlin compiler for `*.kstep.kts` scripts) and a SHA-256
checksum, and nothing is published to Maven Central or Homebrew.

**Geometry, sketches and `kstep import` need the native bridges.** The zip is built without them, so those
features report a clear "unavailable" error there; build from source with a system OpenCascade (Linux
x86-64, or macOS arm64 via Homebrew) to use them. Interoperability is verified with OpenCascade-based readers
(OpenCascade's own readers and FreeCAD), not yet with other CAD/PLM systems.

=== Added

* Sketch extensions (ADR-0032, Welle M). Circle and arc radii can be solver unknowns (`fixedRadius = false`);
  new sketch constraints `radius`, `diameter`, `equalRadius`, `tangent(line, circle)`, `tangent(circle, circle,
  internal)` and `angle(l1, l2, degrees)`; `SolvedSketch.radius(ref)`. New PlaneGCS constraint kinds 7-12 and

=== Fixed

* `kstep import`: a product-structure chain of thousands of levels (a few hundred kilobytes) could exhaust OCCT's
  recursive transfer and crash the JVM; depth and cycles are now checked on the typed entities before the transfer and end
  in `limit_exceeded` (`KSTEP-I-010`). A length unit with conversion factor 0 no longer yields geometry of size 1e100.
* Documentation: ADR-0031, ADR-0032 and ADR-0030 no longer claim OCCT 7.8 compatibility or a Linux CI on 7.8; the
  Linux CI uses 7.9.2 and 7.8 is not tested.
* Export: a part colour together with a face colour no longer aborts with "unexpected entity OVER_RIDING_STYLED_ITEM ...
  refusing to merge it". The overriding item is merged fail-closed: simple instance with four arguments, attached to a
  face, overriding a styled item of the style closure through an acyclic chain of at most 16 that ends at a styled solid
  containing that face; unknown entities are still refused (ADR-0039 S2). Two single-style golden files guard the
  unchanged output.
* Import: the new colour and layer mode made the OCCT transfer quadratic in the number of layer assignments and distinct
  colours (80k layers took 41 s under the global OCCT lock). A pre-transfer typed count now rejects more than 4096 layer
  assignments or 10000 colour definitions with `limit_exceeded` (`KSTEP-I-010`). The count also covers
  `SURFACE_STYLE_TRANSPARENT` and `SURFACE_STYLE_RENDERING_WITH_PROPERTIES` (10000 each), because OCCT's colour table is keyed
  by RGBA and distinct colour x transparency pairs were still quadratic (80k styled items took 67 s). These caps bound
  only the size of the colour table, not the work, because every `STYLED_ITEM` scans that table once (a full table plus
  300k styled items took 116 s). The count therefore also covers `STYLED_ITEM` / `OVER_RIDING_STYLED_ITEM` (at most
  200000) and bounds styled items x (colour definitions + rendering records) to 100000000. The style lists of
  `PRESENTATION_STYLE_ASSIGNMENT`, `SURFACE_SIDE_STYLE` and `STYLED_ITEM` are walked once per styled item too and could
  repeat one reference cheaply (10k styled items x 200k entries took 53 s); lists longer than 64 entries are rejected.
* Import: capped style lists still multiplied, because the colour reader walks styled item -> presentation style
  assignment -> surface side style -> fill area style as nested loops (four lists of 64 = 16.7M steps per styled item;
  100 such items in a 71 kB file took 15 s). The pre-transfer check now sums the weighted expansion cost of all styled
  items (memoised per entity, linear in the file) and rejects more than 10000000 with `limit_exceeded` (`KSTEP-I-010`);
  real files cost 1-3 per styled item. The fill styles of `FILL_AREA_STYLE` and the properties of
  `SURFACE_STYLE_RENDERING_WITH_PROPERTIES` are capped at 64 as well. New constant
  `StepImportLimits.MAX_STYLE_EXPANSION_WORK`.
* Import: an assembly "diamond" (each level using the same sub-assembly twice) has a small depth but 2^levels
  occurrences, and OCCT expanded it during the transfer before the Kotlin occurrence limit fired (28 levels, 56 kB: 69 s).
  The pre-transfer structure check now also counts the part occurrences after expansion on the usage graph and rejects
  more than 10000 (`StepImportLimits.MAX_EXPANDED_OCCURRENCES`, now also checked natively) with `limit_exceeded`
  (`KSTEP-I-010`) in well under a second.
* `kstep import` runs the import in a worker subprocess (ADR-0038). Four audit rounds kept finding new loops inside OCCT
  (a self-overriding `OVER_RIDING_STYLED_ITEM`, deep override chains and `MAPPED_ITEM` chains or cycles ended the process
  with exit 132 and no output at all; override chains, `MAPPED_ITEM` diamonds and shells repeating one face ran into or
  past the 60 s bound). The command now starts a second JVM (same runtime and class path, `-Xmx2g`, no JVM crash banner)
  and only supervises it: a regular end (exit 0 or 1 with one complete report) is passed through unchanged; a timeout
  (60 s, can only be lowered via `-Dkstep.import.timeoutMillis` / `KSTEP_IMPORT_TIMEOUT_MILLIS`; the worker and its
  children are killed), an OutOfMemoryError or an output overflow become `limit_exceeded` (`KSTEP-I-010`), a crash or an
  incomplete report becomes `read_failed` (`KSTEP-I-009`), as text or `--output json`. With `--output json` stdout is
  always exactly one JSON document. The previous in-process watchdog (`Runtime.halt`) printed a JVM fatal-error banner on
  stdout when it ended a native call; it now only bounds an orphaned worker, silently. Cost: one extra JVM start per
  import (about 0.08 s, see ADR-0038). A 100000-deep override chain still crashes OCCT's reader before any pre-scan
  runs; it now ends as one `read_failed` document instead of a silent exit 132. Library callers of `StepImporter` / `OcctKernel.readStep` still run in-process without a time
  or memory bound, and `kstep-mcp` has no import tool.
* Import: three more pre-transfer checks give the known worst cases a structured error in under a second (the worker is
  the guarantee, these are the fast path): `OVER_RIDING_STYLED_ITEM` chains deeper than 16 or cyclic, `MAPPED_ITEM`
  nesting deeper than 32 or cyclic and more than 10000 mapped-item expansions, and more than 250000 face references
  summed over all shells are rejected with `limit_exceeded` (`KSTEP-I-010`). New constants
  `StepImportLimits.MAX_OVERRIDE_DEPTH` and `MAX_MAPPED_ITEM_EXPANSIONS`.
* Tests: a native handle-hygiene test compared the global shape counter exactly and failed once in a full build
  (the cleaner frees shapes of earlier tests asynchronously); it now allows a small growth. A test name was aligned
  with the CI skip guard's marker. The wall-clock bounds of the import limit tests were relaxed to 30 s for slower
  CI runners; the structured limit error is still asserted.

== 0.2.0 — 2026-10-22 (pre-release)

Third pre-release. It turns kSTEP from a product-structure tool into one that models, exports and reads
back geometry: `kstep export` writes product structure and placed assembly geometry, `kstep import` reads
STEP files (kSTEP, OCCT, FreeCAD) back, the OCCT bridge gains booleans, holes, revolve and chamfer, and a
sketch DSL with geometric edge selectors replaces opaque edge indices. As before, the GitHub release carries
a platform-independent JVM-only `kstep-cli-0.2.0.zip` (about 86 MB because it bundles the Kotlin compiler for
`*.kstep.kts` scripts) and a SHA-256 checksum, and nothing is published to Maven Central or Homebrew.

**Geometry, sketches and `kstep import` need the native bridges.** The zip is built without them, so those
features report a clear "unavailable" error there; build from source with a system OpenCascade (Linux
x86-64, or macOS arm64 via Homebrew) to use them. Interoperability is verified with OpenCascade-based readers
(OpenCascade's typed reader and FreeCAD), not yet with other CAD/PLM systems.

== 0.1.0 — 2026-10-19 (pre-release)

First tagged release. It is a *pre-release*: no artifacts are published (Maven Central, etc.), and
the native geometry bridges need system libraries (OpenCascade for the OCCT modules, Eigen headers
for PlaneGCS) and are only verified on Linux x86-64. CI runs on Linux only; the semantic core was
additionally built and tested locally on macOS (geometry tests skipped there). Build from source,
see link:docs/building.adoc[Building].

=== Semantic core (ISO 10303 AP242)

* EXPRESS parser (ANTLR4, `Express.g4`) and a semantic model with Kotlin code generation, verified
  against an excerpt of the real AP242 schema, now sixteen entities
  (`product_definition_occurrence` and the `name`/`description`/`id` attribute entities included).
* Code generation resolves transitive `TYPE` alias chains (cycle- and depth-guarded),
  `ENUMERATION OF (...)` as Kotlin enum classes and closed `SELECT` types as sealed interfaces
  (ADR-0020). `EXTENSIBLE` and `BASED_ON` types are rejected loudly. Only types reachable from the
  emitted entities are generated.
* `SUBTYPE OF` inheritance flattening; `kstep-core` is an ergonomic validating layer over the
  generated types (ADR-0004).
* `DERIVE` attributes as computed properties on generated types (ADR-0021); `get_name_value`,
  `get_description_value` and `get_id_value` intrinsics and the population derives (ADR-0023).
* `WHERE`-rule evaluation including `USEDIN`/`SIZEOF`, `INVERSE` evaluation over a
  reverse-reference index, `UNIQUE` rules `UR1`/`UR2` and the acyclic `WR1` check for assemblies,
  all with size and depth limits (ADR-0022, ADR-0023). Structured violations with stable
  `KSTEP-*` codes; `Ap242ModelValidator` for whole-model checks (opt-in, not yet part of
  `kstep export`).
* Mandatory-attribute presence enforcement (`KSTEP-M-001`, `KSTEP-M-002`).

=== STEP Part 21 and tooling

* STEP Part 21 writer and reader (`kstep-step21`), including tolerant reading and value grammar.
* `*.kstep.kts` scripting host and the `kstep export` CLI command.
* `kstep render` headless preview (SVG, PNG, text and self-contained glTF/GLB).
* `kstep asciidoc`: pre-processing of `kstep` blocks in AsciiDoc documents (ADR-0019).
* MCP server (`kstep mcp`) exposing the entity builders, Part 21 export and `validate_model` as
  LLM tools with structured validation feedback.

=== Geometry and viewer (native bridges; Linux x86-64 verified)

* OpenCascade JNI bridge: boxes, extrusion and fillet, AP242 shape assignment, parametric feature
  history (foundation), triangulation.
* PlaneGCS 2D constraint solver bridge: coincidence, distance, horizontal/vertical, point-on-line,
  parallel and perpendicular.
* Interactive Compose Desktop viewer: orbit, zoom, pan, multi-shape scenes, per-part colors and
  smooth per-vertex normals (ADR-0018).

=== Known limitations

* No published artifacts; build from source (JDK 21).
* Part 21 output is verified by self-round-trip only. Interoperability with external CAD/PLM tools
  (for example FreeCAD) has not been validated; a fixture for the manual check lives in
  `kstep-tests`. Update (0.1.1): FreeCAD 1.x reads the files without error (0 objects, no
  geometry is written) and an OpenCascade typed reader resolves the product structure; geometry
  and other tools remain unverified.
* `kstep export` and the script host do not run model-level validation yet; an assembly cycle
  is not detected on export (exit code 0). Update (0.1.1): `kstep export --validate` now
  does this opt-in; without the flag a cycle is still exported.
* `QUERY` and general EXPRESS functions are not evaluated; `INVERSE`/`USEDIN` roles over entities
  that are not modelled follow the assumptions documented in ADR-0022/0023.
* The AP242 schema is a vendored excerpt, not the full standard.
* The LLM benchmark is deferred to a later version.
