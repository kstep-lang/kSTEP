== Why kSTEP

LLMs are strong in popular, high-resource languages (Kotlin, Java, Python)
but measurably weak at generating external, low-resource DSLs — and STEP's
native exchange format (Part 21, graphs of `#123`-style entity references)
is a particularly hostile one to read or write directly.

kSTEP applies **Typed Domain Grounding (TDG)** — the pattern already
validated by its sibling project, https://github.com/kuml-dev/kUML[kUML]:
expose a domain as a type-safe, embedded Kotlin DSL with semantic
validation and structured errors, so that both human developers and LLM
agents can work in it reliably. The syntax stays Kotlin (high-resource);
only the vocabulary is domain-specific, enforced by the type system. A
strict type system, a compiler, and structured validation errors form a
feedback loop the LLM can act on directly, without a separate benchmark
or fine-tuning step. kSTEP compiles that DSL down to the neutral,
standardized ISO 10303 exchange format.

== Vision

kSTEP is not "just another CAD tool." The ambition is to cover the
**entire STEP standard (ISO 10303)**: CAD is the entry point, not the
boundary. STEP also spans manufacturing (STEP-NC), electrical and
electronics, kinematics, composites, FEM/simulation and plant/process data,
each carved out as its own Application Protocol (AP242, AP238, AP210, AP209,
and others). Those APs are the building blocks kSTEP intends to grow into.

It is the deliberate third way between classic, GUI-centric CAD suites and
niche code-first CAD: code-first, AI-first and STEP-native instead of
proprietary. It is the same thesis as its sibling project
https://github.com/kuml-dev/kUML[kUML] in the UML/SysML space, applied to the
engineering domain.

V1 deliberately starts narrow: a single Application Protocol (AP242), scoped
down to product structure and metadata (see
link:docs/roadmap.adoc[Roadmap] and kSTEP-ADR-0001). Geometry was added
afterwards as an optional layer.

== Status

The current release is **v0.5.0** (2026-11-17), a pre-release; changes on
the `master` branch after it are listed under "Unreleased" in the
link:CHANGELOG.adoc[CHANGELOG]. What is in place:

* EXPRESS parser, semantic model and Kotlin code generation, with an
  AP242 V1 entity layer (`kstep-core`) and STEP Part 21 export/import.
* A Kotlin scripting host for `*.kstep.kts` files, the `kstep` command-line
  tool (`export`, `import`, `render`, `asciidoc`, `mcp`) and an MCP server.
* Optional geometry: an OpenCascade (OCCT) bridge (primitives, booleans, holes,
  fillet/chamfer, mirror, uniform scale, shell, pocket or hole from a face, draft,
  thickening, edge/face/vertex selection, persistent edge names including the inner
  wall of an INWARD shell, a feature history with undo/redo), a PlaneGCS sketch
  solver, placed assemblies, colours (with transparency, also on edges and per placed occurrence) and layers
  in export and import, and headless preview rendering. Both native bridges need
  system libraries (Linux x86-64 or macOS arm64) and are part of neither the
  release zip nor the Maven Central jars.

Not yet available: PMI, the STEP colour transparency in the desktop viewer
(`kstep render` draws it; the desktop only has the manual per-part visibility), names for pocket walls and drafted or thickened faces, Windows and
Intel Mac support for the native bridges, and interoperability checks beyond
OpenCascade-based readers (OCCT, FreeCAD).

The wave-by-wave log is in link:docs/status.adoc[Status]; open points are in
the link:docs/roadmap.adoc[Roadmap]. Both say what is and is not verified.

== Quickstart

Requires JDK 21. Build the command-line tool and export a product structure
to a STEP Part 21 file (the native geometry bridges are optional and not
needed for this):

[source,shell]
----
./gradlew clean :kstep-cli:installDist
----

Save this script as `bracket.kstep.kts`:

[source,kotlin]
----
val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext {
    name = "engineering"; frameOfReference = appCtx; disciplineType = "mechanical"
}.getOrThrow()
val defCtx = productDefinitionContext {
    name = "engineering"; frameOfReference = appCtx; lifeCycleStage = "design"
}.getOrThrow()

val bracket = product("BRK-001") { name = "Bracket"; frameOfReference = setOf(prodCtx) }.getOrThrow()
val bracketFormation = productDefinitionFormation("BRK-001-F") { ofProduct = bracket }.getOrThrow()
val definition = productDefinition("BRK-001-D") {
    formation = bracketFormation
    frameOfReference = defCtx
}.getOrThrow()

stepFile(fileName = "bracket.step") {
    root(definition)
}
----

[source,shell]
----
kstep-cli/build/install/kstep-cli/bin/kstep-cli export bracket.kstep.kts
# Exported 1 root(s) to bracket.step
----

The installed launcher is named `kstep-cli`; the documentation calls the
command `kstep`. `kstep convert` moves between a script and a Markdown note
holding it in a fenced `kstep` block, without running anything:

[source,shell]
----
kstep-cli/build/install/kstep-cli/bin/kstep-cli convert bracket.kstep.kts --to okf   # writes bracket.md
kstep-cli/build/install/kstep-cli/bin/kstep-cli convert bracket.md --to kts          # writes bracket.kstep.kts
kstep-cli/build/install/kstep-cli/bin/kstep-cli convert scripts --to okf --out notes --output json   # a whole folder, JSON report
----

The same pipeline as a library, parsing an EXPRESS schema and
generating Kotlin source:

[source,kotlin]
----
import dev.kstep.express.codegen.ExpressKotlinCodeGenerator
import dev.kstep.express.semantic.ExpressSemanticModelBuilder

val schema = """
    SCHEMA example_schema;
      ENTITY product;
        id   : STRING;
        name : STRING;
      END_ENTITY;
    END_SCHEMA;
""".trimIndent()

val model = ExpressSemanticModelBuilder.build(schema)
println(
    ExpressKotlinCodeGenerator.generateFileSource(
        model.schemas.single(),
        "dev.kstep.generated.example",
    ),
)
// package dev.kstep.generated.example
//
// import kotlin.String
//
// public data class Product(
//   public val id: String,
//   public val name: String,
// )
----

More examples (validation, geometry, sketches, rendering, import) are in
link:docs/usage.adoc[Usage].

== Modules

[cols="1,3",options="header"]
|===
| Module | Purpose

| `kstep-core`
| Core DSL types, validation results and the generated AP242 V1 entity classes.

| `kstep-express`
| ANTLR4 EXPRESS parser, semantic model and Kotlin code generator.

| `kstep-step21`
| STEP Part 21 reader and writer for the AP242 entities.

| `kstep-script`
| Kotlin scripting host for `*.kstep.kts` scripts.

| `kstep-cli`
| Command-line entry point (`export`, `render`, `import`, `asciidoc`, `convert`, `mcp`). `kstep export --target/--all-targets` writes the file names a script declares in its `export { }` block (ADR-0065).

| `kstep-mcp`
| MCP server exposing the entity builders and Part 21 export as LLM tools.

| `kstep-geometry`
| Optional OpenCascade (OCCT) JNI bridge for B-Rep geometry.

| `kstep-constraints`
| Optional PlaneGCS bridge for 2D geometric constraints.

| `kstep-sketch`
| Constraint-sketch DSL.

| `kstep-shape`
| AP242 shape assignment: merges product structure with B-Rep solids.

| `kstep-render`
| Headless mesh projection and SVG/PNG/text/glTF rendering, plus STL/3MF mesh export (`kstep render -f stl|3mf`).

| `kstep-preview`
| Shared headless preview pipeline behind `render` and `asciidoc`.

| `kstep-docs:kstep-asciidoc`
| Asciidoctor pre-processing integration (`kstep asciidoc`).

| `kstep-viewer`
| Interactive OCCT shape viewer (Compose Desktop).

| `kstep-desktop`
| Live preview of a `*.kstep.kts` script (Compose Desktop, `./gradlew :kstep-desktop:run`): re-renders on save in a
  supervised worker process; with a small script editor (syntax colouring, error marks, crash-safe save). Click a part to select it (Escape or a click on
  empty space clears), hover tints it, and a panel shows its name, size, centroid, colour and position. An assembly tree beside the
  canvas (toggle with the Tree icon in the toolbar, whose name shows on hover; Up/Down, Left/Right, Home/End, Enter, Escape when it has focus) selects whole
  sub-assemblies; if the tree cannot be trusted it stays hidden with the warning `KSTEP-D-013` and click selection still works.
  Parts and sub-assemblies can be made transparent or hidden (eye column in the tree, toolbar, keys `T`, `V`, `I`, `Shift+V`).
  The `Export...` dialog (Cmd/Ctrl+E) writes the saved script as STEP AP242, GLB, STL or 3MF: the script runs in a supervised worker, the
  result is validated and moved to the target atomically, an existing file is replaced only after confirmation (ADR-0057; no new dependency).
  A script can suggest the file names with an `export { }` block, and the dialog remembers the last format and folder (ADR-0063).
  Files a script reads with `readInput("x")`/`inputFile("x")` next to itself are watched too (ADR-0080).
  `Open Folder...` (Cmd/Ctrl+Shift+O) opens a folder of Markdown notes as a knowledge workspace: the fenced `kstep` block under the
  cursor is previewed live (ADR-0058; export and AI are not available there yet).
  `Convert...` in the File menu turns a note into scripts or a script into a note, for one file or a folder; existing files are replaced only after you confirm the list (ADR-0078).
  An optional AI panel (AI Panel icon in the toolbar, Cmd/Ctrl+K) proposes changes from a description as a diff you accept or discard (ADR-0056).
  *Privacy:* nothing is sent before you agree in a dialog; only your prompt and, if you tick it, the current script go to the
  provider (Anthropic, `api.anthropic.com`), never keys, file paths or other files. The API key is kept in the system keychain,
  for this session only, or read from `KSTEP_AI_ANTHROPIC_KEY`; it is never written to a file. To check a proposal, the generated
  script is run on this computer before you have read it, in a sandbox (macOS `sandbox-exec`, Linux `bubblewrap`) without network
  access that can write only to its session folder. *It can still read your files*, including a key in the system keychain, but
  cannot send what it reads out. Windows and Linux without `bubblewrap` have no such sandbox: there the script is not run and the
  proposal is shown as "not checked", so read the diff before you apply it. The live preview, the export and the blocks of the knowledge workspace run your own scripts in the same kind of
  sandbox (macOS `sandbox-exec`, Linux `bubblewrap`): no network, writing only in their session folder, reading stays
  allowed. Where no sandbox works the scripts still run, and the status line shows "Script runs without sandbox". The
  Linux variant is not yet confirmed in CI.

| `kstep-desktop-ai`
| Logic of the desktop AI panel (not published): repair loop, key store access, consent settings, Koog-based Anthropic client
  behind a hardened transport. Pure JVM, never on the worker class path or in the CLI zip.

| `kstep-tests`
| Cross-module integration tests (Kotest).
|===

Details per module: link:docs/modules.adoc[Modules].

== Native runtime archive (opt-in)

`./gradlew :kstep-cli:nativeRuntimeZip -Pkstep.native.embedInJar=false` builds a host-platform archive with the OCCT and
PlaneGCS bridges as plain files and a `bin/kstep` launcher. OCCT 7.9.x must be installed separately. Not part of releases;
see ADR-0050 and `docs/building.adoc`.
