= Interop check: read kSTEP Part 21 with OpenCascade

`read_step_structure.cpp` reads a STEP file with OpenCascade's *typed* STEP model (no geometry
transfer) and prints the product structure it found: `PRODUCT`, `PRODUCT_DEFINITION`,
`NEXT_ASSEMBLY_USAGE_OCCURRENCE` (with relating/related ends), `APPROVAL`, the entity-type
histogram, the number of undefined entities and the OCCT model check (fails/warnings). It is an
independent reader for the product-structure half of the external-interop bar described in the
README; it does not prove geometry interop.

== Build and run

macOS (Homebrew):

[source,bash]
----
brew install opencascade
P="$(brew --prefix opencascade)"
c++ -std=c++17 -I"$P/include/opencascade" -L"$P/lib" -Wl,-rpath,"$P/lib" \
  scripts/interop/read_step_structure.cpp -o read_step_structure \
  -lTKDESTEP -lTKXSBase -lTKernel -lTKMath
./read_step_structure out.step
----

Linux (Debian/Ubuntu, see the README 'Building' section for the OCCT packages): same command with
`-I/usr/include/opencascade` and `-L/usr/lib/x86_64-linux-gnu`.

Produce a file with `kstep export script.kstep.kts --out out.step`.

== Result of 2026-10-22 (OpenCascade 7.9.3, macOS arm64)

`hello-assembly.step`: read status `RetDone`, 14 entities, none undefined, model check 0 fails and
0 warnings; products Housing (`HSG-001`), Bracket (`BRK-001`) and Screw (`SCR-001`) with their
definitions and both assembly usages resolved to the correct ends. A deliberately broken file is
rejected with a line-accurate error. Not covered: geometry, other CAD/PLM readers, full AP242
schema conformance, a lossless write-back round trip.

== Result of 2026-10-22, geometry-carrying files (OpenCascade 7.9.3, macOS arm64)

Two files written by the OCCT JNI bridge during the test run (`box-ap242.step` from
`OcctBridgeSmokeTest`, `extruded-filleted.step` from `OcctFeatureOperationsTest`; `kstep export`
did not merge geometry at that time) were checked:

* `read_step_structure`: read status `RetDone`, 0 undefined entities, model check 0 fails and 0
  warnings; the entity histogram contains one `StepShape_AdvancedBrepShapeRepresentation` and one
  `StepShape_ManifoldSolidBrep` per file.
* FreeCAD 1.1.4 (`freecadcmd`, `Import.insert`): one object of type `Solid`, valid, volume 24000.0
  (box) and 23785.398 (extruded and filleted).

This proves that OCCT and FreeCAD read the shape representation written by the bridge. It does not
prove interoperability of the full kSTEP Part 21 output with geometry merged in; that is covered by the
next section.

== Result of 2026-10-22, `kstep export` with geometry (ADR-0027)

[source,bash]
----
kstep export kstep-tests/src/test/resources/export-box-20x30x40.kstep.kts --out box.step
kstep export kstep-tests/src/test/resources/export-assembly-geometry.kstep.kts --out assembly.step
./read_step_structure box.step
./read_step_structure assembly.step
----

* `read_step_structure`: both files `RetDone`, 0 undefined entities, model check 0 fails and 0
  warnings. `box.step`: 350 entities, 1 product, 1 `ProductDefinitionShape`, 1
  `AdvancedBrepShapeRepresentation`, 6 `AdvancedFace`. `assembly.step`: 696 entities, 2 products,
  1 assembly usage with both ends resolved, 2 shape representations, 12 `AdvancedFace`.
* FreeCAD 1.1.4 `Part.read('box.step')`: `Solid True 24000.0 6`.
* FreeCAD 1.1.4 on `assembly.step`: only the root product `Housing` arrives (one `Part::Feature`,
  volume 60000.0, 6 faces); the child `Bracket` geometry is not transferred and there is no
  hierarchy. The same two parts exported as two plain roots (no usage) both arrive (`Housing`
  60000.0, `Bracket` 1000.0). Reason: no placement transformation links the child representation to
  the assembly, so an OCCT/FreeCAD reader has nothing to position it with.
