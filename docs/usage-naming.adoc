= Usage: persistent naming of generated edges

== Persistent naming of generated edges and undo/redo (Welle N)

A geometric selector describes where an edge IS; after a parameter change it can hit different edges. For the
edges an extrude or revolve GENERATES, `GeneratedEdges` names them by the profile definition instead ("the edge
swept from corner `p2` of feature 0"), which survives the change:

[source,kotlin]
----
// export-sketch-generated-fillet.kstep.kts (excerpt): the plate's four corners are the sketch points p0..p3
val features =
    FeatureSequence(
        listOf(
            plate, // sketchFeature(mapOf("width" to 40.0), SketchOperation.Extrude(10.0)) { p -> rectangle(...) }
            SelectedFilletFeature(0, GeneratedEdges(0, SketchSources.corners("p0", "p1", "p2", "p3"), expected = 4), 2.0),
        ),
    )
// width 40: volume 7965.664, 10 faces;  plate.withParameter("width", 60.0): 11965.664, 10 faces

// Without a sketch, directly on the kernel:
OcctKernel.extrudeProfileNamed(profile, 10.0, GenerationSources.profileVertices(4)).use { named ->
    OcctKernel.fillet(named, GenerationSources.profileVertices(4), 2.0, expected = 4)
}
----

A vertex source has `SIDE` images, an edge source (`ProfileEdge`, `SketchEdgeOf`) has `START` and `END` copies. Nothing is
guessed: a source without an image (a vertex on the axis of a full revolve), a deleted edge or a wrong `expected`
count is an `EdgeNamingException` listing candidates (`KSTEP-S-011`; `hello-generated-edges-unresolved.kstep.kts`).
Sketch corners are called `p<index>` by default, counting all points of the sketch, so pass
`rectangle(..., names = listOf("bl", "br", "tr", "tl"))` for stable names. Edges generated by fillet, chamfer or
boolean operations are named separately, see the next section; multi-body sketches cannot be named yet (ADR-0033).

`FeatureHistory` adds undo/redo over a `FeatureSequence`; it holds immutable snapshots and no shapes, so undoing
costs nothing until `rebuild()`:

[source,kotlin]
----
val history = FeatureHistory()
history.add(BoxFeature(40.0, 20.0, 10.0))
history.add(SelectedFilletFeature(0, SelectEdges(Edges.parallelTo(Direction3.Z), expected = 4), 2.0))
history.add(HoleFeature(1, 8.0, 20.0, 20.0, 10.0, 15.0))   // volume 7463.009, 11 faces
history.undo(); history.redo()
history.update(2) { (it as HoleFeature).copy(diameter = 10.0) }   // volume 7180.266
val shape = history.rebuild().final
----

Adding, removing and moving keep the indices of later features consistent; removing a feature that a later one
still refers to is refused with the dependents listed. The history lives in memory only (`export-feature-history-undo.kstep.kts`).

== Naming the edges of fillets, booleans and holes (Welle N2)

`GeneratedEdges` also works when the generator is a derived feature. The source names what the operation was
GIVEN, not what it produced: the drill of a hole, the faces of a boolean, the edges a fillet rounded. OCCT's own
history (`Generated()`) maps it to the result edges, so the name survives a parameter change:

[source,kotlin]
----
// export-hole-rim-fillet.kstep.kts: round the ring at which the drill ENTERS the plate
val features =
    FeatureSequence(
        listOf(
            BoxFeature(40.0, 40.0, 10.0),
            HoleFeature(0, 8.0, 12.0, 20.0, 20.0, 11.0),          // drills downwards from z = 11
            SelectedFilletFeature(1, GeneratedEdges(1, listOf(HoleWall), GeneratedRole.RIM_ENTRY, expected = 1), 1.0),
        ),
    )
// 40x40x10 plate: volume 15491.650, 8 faces;  BoxFeature(60.0, ...): 23491.650, 8 faces
----

[cols="2,3,3"]
|===
| Generator | Sources | Role of the images

| fillet, chamfer
| `BlendedEdges`, `OperandEdges(0, selector)`
| `BOUNDARY`: the edges of the blend face that border a face the operation did not create

| boolean
| `BooleanSection`, `OperandFaces(0 or 1, faceSelector)`
| `SECTION`: where the named faces were cut by the other body (after coplanar faces were merged)

| hole
| `HoleWall`, plus the boolean sources
| `SECTION`; `RIM_ENTRY` / `RIM_EXIT`: the ring nearest to / farthest from the start point along the drill direction. Both rim roles raise an `EdgeNamingException` when the drill breaks out through a side face, when a
ring lies on a plane face inclined more than 45 degrees to the drill, or when a single ring lies on a curved face
(for example a blind hole into a rod); use `SECTION` then
|===

Nothing is guessed. A blind hole has no `RIM_EXIT`, a hole that breaks out sideways has neither rim role (`SECTION` remains), a source that picks an edge the operation did not round has no
image, and a wrong `expected` count is an `EdgeNamingException` with the generated candidates (`KSTEP-S-011`,
`hello-derived-edges-unresolved.kstep.kts`). The combinations are checked before any native call. `OperandEdges` is
not offered for booleans because OCCT reports vertices, not edges, for the edges of a boolean (spike result in
ADR-0034). Corner blends, persistent history across a change of the source topology and multi-body generators are
not covered. `scripts/interop/verify-derived-naming.sh` re-checks the example exports with OCCT and FreeCAD.
