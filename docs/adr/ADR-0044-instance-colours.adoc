= ADR-0044: Instance colours in the STEP export and import (Welle V)
:toc:

== Status

Accepted, implemented (kSTEP Welle V). It builds the follow-up that ADR-0042 measured but did not build: one placed
occurrence of a part (one assembly usage) gets a colour of its own, so a part used twice can be red once and blue once.
The gate that ADR-0042 named (a C++ mini test that OCCT's reader reads a hand-written pattern as an instance colour) was
run first and passed; every number below comes from `scripts/interop/spike_instance_colour_read.cpp` and
`scripts/interop/verify-export-instance-colours.sh` (OCCT 7.9.3, macOS arm64, FreeCAD as installed on the same machine).

== Context

kSTEP builds the assembly itself (`Ap242PlacementBridge`: `CONTEXT_DEPENDENT_SHAPE_REPRESENTATION`,
`NEXT_ASSEMBLY_USAGE_OCCURRENCE`, `REPRESENTATION_RELATIONSHIP_WITH_TRANSFORMATION`, no `MAPPED_ITEM`). OCCT's writer cannot be
asked for an instance colour in that mode (ADR-0042: in assembly mode 0 it writes none at all, and in mode 2 it writes the
style twice). So the entities are written by hand, and the import has to read them back. The OCCT reader returns such a style
as a colour of the component label ("component 2 blue"); the importer used to count it in `presentation.instanceStylesIgnored`
and drop it.

== Measurements (the gate)

The fixtures are a 10 x 20 x 30 box used twice, instance 1 at the origin and instance 2 at x = 50, exported by kSTEP without
colour, with the pattern appended at the very end by `scripts/interop/make_instance_colour_fixtures.py`. The reader is
`STEPCAFControl_Reader` with colour mode on; the colours are read through the RGBA overload (`XCAFDoc_ColorSurf`, then
`XCAFDoc_ColorGen`) of the component label, of the referred part label and of the free shape.

[cols="1,4,5",options="header"]
|===
| Id | Scenario | OCCT reads
| G1 | only instance 2 blue | component 2 blue, component 1 none, part none, assembly none; 2 components, volume 12000
| G2 | instance 1 red, instance 2 blue | both component colours; part and assembly none
| G3 | part orange (OCCT's own `MECHANICAL_DESIGN_GEOMETRIC_PRESENTATION_REPRESENTATION`) plus instance 2 blue; two such representations in the file | part orange, component 2 blue, component 1 none
| G4 | a dedicated axis in the style's representation instead of the placement axis of the usage | same as G1, so the shared axis is enough and the four extra entities are not needed
| G5 | a child with two solids (assembly mode 0): one `STYLED_ITEM` per solid, one shared `PRESENTATION_STYLE_BY_CONTEXT` | component 2 blue, component 1 none, part none (volume 12128)
| G6 | `COLOUR_RGB` 192/255, 0.3, 0.25 and the mirrored one | both within 1e-6 (the reader converts with `Quantity_TOC_sRGB`; 1.0 comes back as 0.9999999999999999)
| G7 (negative) | the same pattern without the `SHAPE_DEFINITION_REPRESENTATION` | not an instance colour: component 2 none, *and the shared part turns blue*, so both occurrences would be coloured
| G8 | a second `PRODUCT_DEFINITION_SHAPE('Placement', ...)` on the usage instead of reusing the existing one | same as G1
|===

G7 is the reason for the `SHAPE_DEFINITION_REPRESENTATION`: without it OCCT silently repaints the product, a wrong result
without any warning. G1 and G8 both work; kSTEP reuses the `PRODUCT_DEFINITION_SHAPE('Placement', ...)` that
`Ap242PlacementBridge` already wrote for the usage, which is also what OCCT's own writer does (the usage then carries one
`CONTEXT_DEPENDENT_SHAPE_REPRESENTATION` and one `SHAPE_DEFINITION_REPRESENTATION` on the same `PRODUCT_DEFINITION_SHAPE`).
This is ten entities per coloured usage for a one-solid child (one more `STYLED_ITEM` per further solid) and one
`MECHANICAL_DESIGN_GEOMETRIC_PRESENTATION_REPRESENTATION` for the file; the plan assumed eleven with a new
`PRODUCT_DEFINITION_SHAPE`, which G8 shows to be unnecessary.

Also measured: OCCT's writer does not write an instance layer at all (scenario `instance-layer` of
`spike_export_styles.cpp` writes no `PRESENTATION_LAYER_ASSIGNMENT`), and FreeCAD loads the file with the same two boxes,
volume 12000 and the same bounding boxes as the file without colour (headless FreeCAD reads no colours; this is noted, not
counted as a check). Hand calculation for the end-to-end example: one part (volume 6000), two occurrences, total volume 12000,
the second occurrence 50 mm to the right, two coloured targets.

== Decisions

D1:: *`UsageStyle(usage, colour)`* (kstep-shape, next to `UsagePlacement`) is produced by the script DSL's
`styleInstance(usage, colour)`, carried in the new additive field `KStepModel.usageStyles` and passed to
`Ap242ShapeExporter.export(..., usageStyles)` (a new default parameter, so every existing caller is unchanged). The colour
belongs to the usage, like `place(...)`, and is independent of the colour of the part.

D2:: *The entities come last.* They are appended behind `PRODUCT_RELATED_PRODUCT_CATEGORY`, with the ids after it, so a file
without instance colours is byte for byte a prefix of the same file with them (a test compares the placed-assembly golden with
the same script plus two `styleInstance` calls). Without instance colours nothing in the exporter runs differently, so every
existing golden stays byte-identical.

D3:: *Own allow-list and a self-check.* `Ap242InstanceStyleBridge.INSTANCE_STYLE_ENTITY_NAMES` lists exactly the eleven names
the bridge writes. It is not merged into `Ap242GeometryExtraction.STYLE_ENTITY_NAMES`: OCCT never writes
`PRESENTATION_STYLE_BY_CONTEXT` for a single part, so the extraction of OCCT's own output stays fail closed against it (a test
pins this). After building, `verify` checks that every entity is a simple instance on the allow-list, ids are unique, and every
reference goes to an entity of the same list or to exactly the ids the bridge was given (the `PRODUCT_DEFINITION_SHAPE` and
the placement axis of the usage, the representation context, the solids of the child); a violation is a
`ShapeExportException`.

D4:: *Limits, all fail closed (`ShapeExportException`, code `KSTEP-S-008` in the CLI).* Only opaque colours (_superseded by the Welle Y amendment below_: a translucent colour is accepted; an invalid alpha is still refused in the script with `KSTEP-S-012`); a usage must be a geometric usage of the plan (a root with a geometric
child); its child must have a shape of its own, so one occurrence of a sub-assembly cannot be coloured (_partly superseded by ADR-0046_: a sub-assembly occurrence is now coloured through the solids of its leaves; the following wording is the state of Welle V; it would need a
`SHAPE_REPRESENTATION_RELATIONSHIP` path or a `SHAPE_DEFINITION` chain per leaf, which is not measured); a second colour for one
usage is `KSTEP-S-014` in the script; at most 4096 instance colours (the cap of geometric usages). Children with several solids
are supported (G5). No layers on instances (OCCT writes none, the reader returns none; gate failed in Welle Z, see ADR-0047), no colours per context path of a
nested usage (`SHUO`), no per-face colours on an occurrence.

D5:: *The importer reports them.* The native collector records a surface colour of a component label with the new target
`INSTANCE` (appended to `XcafStyleTarget` so the ordinals of the others stay stable) on the COMPONENT node, sub-index 0. The
Kotlin side checks that `INSTANCE` records, and only they, point to COMPONENT nodes with sub-index 0. `ImportedComponent.color`
is new, the JSON gets `components[].colour` (always present, `null` without a colour, like the other colour keys, so additive;
there is no format version field) and the text report appends `  colour (r, g, b)` to the component line only when a colour
exists, so the text of every file without instance colours is byte-identical. The part-, face- and edge-paths filter by target
and never see `INSTANCE` records.

D6:: *Changed meaning of two counters.* `presentation.instanceStylesIgnored` now counts only what is still not read: a layer on
a component or a colour that exists only as a curve colour (once per component); surface colours on instances are no longer
ignored. `presentation.coloredTargets` counts instance colours too (like edge colours in ADR-0042 D6), so it rises for foreign
files that carry them. The warning "colour/layer assignments on assembly instances are not reported" names only the remainder.
The native caps are unchanged: an instance colour is one more record under `kMaxStyleRecords` (`styleTruncated` otherwise), and
`PRESENTATION_STYLE_BY_CONTEXT`, a subtype of `STYLED_ITEM`'s style list entity `PresentationStyleAssignment`, is covered by
the pre-transfer list-length cap through `IsKind` (ADR-0038).

D7:: *`kstep render` ignores instance colours and the effective colour per occurrence is not computed in this wave.* Both
are implemented since ADR-0045 (Welle W); the render ignored alpha until the Welle Y amendment below.

== Not built / follow-ups

* Done in ADR-0046: colours on occurrences of sub-assemblies. Done in the Welle Y amendment below: transparency on instance colours and in the render. Still open: path-exact colours, layers on instances (gate failed in Welle Z, see ADR-0047).
* Done in ADR-0045: the effective colour per occurrence in `kstep import` and instance colours in `kstep render`.
* Interoperability is checked with OCCT's reader and FreeCAD (geometry); other CAD systems are not covered.

== Amendment: transparent instance colours (Welle Y)

Status: accepted, implemented. Closes the follow-up "transparency on instance colours". The gate passed, so no separate ADR
(planned ADR-0047 for a failed gate) was needed.

*Gate.* OCCT 7.9.3 (macOS arm64), `scripts/interop/verify-export-instance-transparency.sh`, CI test `InstanceTransparencyOcctGateTest`.
The hand-written chain is the one OCCT's own writer produces for a part alpha (ADR-0042):
`SURFACE_SIDE_STYLE('', (#fillArea, #rendering))` with `#rendering = SURFACE_STYLE_RENDERING_WITH_PROPERTIES(.NORMAL_SHADING.,
#colourRgb, (#t))` and `#t = SURFACE_STYLE_TRANSPARENT(1 - alpha)`; the rendering refers to the same `COLOUR_RGB` as the fill.
`make_instance_colour_fixtures.py` writes it for a fourth colour component below 1.

[cols="1,3,3",options="header"]
|===
|Scenario |Setup |OCCT reads
|Y0 (informative) |OCCT's own writer, `SetColor(component, blue alpha 0.5)`, assembly mode 2 |the same chain, one `STYLED_ITEM` and one `PRESENTATION_STYLE_BY_CONTEXT` per component; read back as blue 0.5
|Y1 |box twice, instance 2 blue alpha 0.5 |component 2 (0,0,1,0.5), component 1, the part and the assembly none, volume 12000; effective leaf 2 blue 0.5, leaf 1 none
|Y2 |instance 1 red opaque, instance 2 blue alpha 0.25 |alpha 1.0 and 0.25
|Y3 |orange opaque part plus instance 2 blue 0.5 |part orange alpha 1 (not repainted, no alpha leak), component 2 blue 0.5
|Y3b |orange part with alpha 0.5 plus instance 2 blue opaque |effective leaf 2 blue 1.0: the winning source supplies its whole colour, alpha included
|Y4 |ASM > SUB x2 > BOX x2, SUB occurrence 2 blue 0.5 |leaves x=100 and x=120 blue 0.5, x=0 and x=20 none, part none, volume 24000
|Y5 |SUB occurrence 2 blue 0.25 plus inner usage red opaque |x=0 and x=100 red 1.0, x=20 none, x=120 blue 0.25 (the ADR-0046 hand calculation)
|Y6 |alpha 0.0, 192/255, 0.3, 0.999999 |all within 1e-6 (OCCT stores alpha as a float, 6e-8). CI: the committed `gate-Y6.step` covers 192/255; all four values are covered by the export and import round trip in `CliExportOcctInstanceColourIntegrationTest`
|Y7 (negative) |Y1 without the `SHAPE_DEFINITION_REPRESENTATION` |OCCT repaints the shared part, alpha included: the SDR stays mandatory
|Y8 |FreeCAD loads Y1 and Y4 |as geometry (volume); colours are not readable headless
|===

*Decisions.*

D1:: *Same chain as OCCT's writer, transparency `t = 1 - alpha`.* The two entities `SURFACE_STYLE_TRANSPARENT` and
`SURFACE_STYLE_RENDERING_WITH_PROPERTIES` are written only for alpha < 1, after `SURFACE_STYLE_FILL_AREA` and before
`SURFACE_SIDE_STYLE`. For an opaque colour no id is added and no byte changes, so every earlier export and the prefix chain
(plain, parts, sub-assemblies) stay byte-identical.
D2:: *Both allow-lists grow to thirteen names* (the two entities above). They stay two separate sets and are still NOT merged
into the extraction allow-list `Ap242GeometryExtraction.STYLE_ENTITY_NAMES`, which does not know `PRESENTATION_STYLE_BY_CONTEXT`.
D3:: *The opacity checks go.* `KStepModel.styleInstance` and `Ap242InstanceStyleBridge.plan` no longer refuse alpha < 1; the old
tests are replaced, not relaxed. An alpha that is not finite or outside 0..1 is refused by `StepColour` with `KSTEP-S-012`;
`plan` keeps an unreachable defence-in-depth check. No new error code. `Ap242InstanceStyleReader` accepts a one- or
two-item side style and checks `NORMAL_SHADING`, the same colour reference and one finite transparency in 0..1, otherwise
`IllegalArgumentException`.
D4:: *Precedence is unchanged; alpha belongs to the winning colour* (Y3b, Y5). No mixing of RGB from one source and alpha from
another. Import needed no code change: the bridge already reads the RGBA overload for component labels, and
`RgbColor.alpha` is already in the JSON and the text report (` alpha 0.5`). Hostile alpha from a foreign file (`-0.5`, `1.5`,
`1.E400` in `SURFACE_STYLE_TRANSPARENT`) never leaves 0..1: the existing native-to-Kotlin mapping clamps, and
`InstanceTransparencyOcctGateTest` pins the invariant.
D5:: *Opacity in `kstep render` (supersedes "the preview stays opaque" of ADR-0042 and D6 of ADR-0045).* `MeshColor` gets
`a: Double = 1.0` (source compatible, a binary change of the constructor, as with `PlacedInstance` in ADR-0046). SVG: the
element `opacity` on a translucent polygon (not `fill-opacity`, which would blend the anti-seam stroke twice). PNG: one
`Area` composite of fill and stroke for a < 1. GLB: `COLOR_0` as `VEC4` and `alphaMode BLEND` only when some triangle is
translucent. Everything opaque is byte-identical. Part colours with alpha become translucent in the render too, because
part and instance colours run through the same path.

*Limits.* No path-exact colours (`SHUO`), no layers on instances. The viewer (`kstep-viewer`) still draws opaque. Translucent
triangles are painted in the existing back-to-front order without re-sorting, so mutually penetrating translucent parts show
the usual painter artefacts. `kstep import --render` uses its own fixed palette. Not verified with readers other than
OpenCascade-based ones and FreeCAD geometry.
