= ADR-0009: AP242 shape assignment -- merging kstep-core product structure with OCCT geometry (Geometrie Welle 4)
:toc:

== Status

Accepted, implemented (kSTEP Geometrie Welle 4). Answers the open design
question ADR-0005's Folge-Wellen table left for this wave: *"`STEPCAFControl_Writer`/XCAF
vs. a Part-21-level merge"* -- decided below as a Part-21-level merge, plus a
new module, `kstep-shape`, and a load-bearing extension to `kstep-step21`'s
own value grammar.

== Context

`kstep-step21` (M2) writes a validated `kstep-core` AP242 product structure
with no geometry. `kstep-geometry` (Geometrie Welle 1/5a) writes a real OCCT
B-Rep solid to STEP with no `kstep-core` involvement at all -- but not "pure
geometry": `OcctShape.writeStepFile` emits a *complete* AP242 product
structure of its own, generated by OCCT itself, e.g. for a 20x30x40mm box:

[source]
----
#1 = APPLICATION_PROTOCOL_DEFINITION('international standard',
  'ap242_managed_model_based_3d_engineering',2013,#2);
#2 = APPLICATION_CONTEXT('Managed model based 3d engineering');
#3 = SHAPE_DEFINITION_REPRESENTATION(#4,#10);      <1>
#4 = PRODUCT_DEFINITION_SHAPE('','',#5);           <1>
#5 = PRODUCT_DEFINITION('design','',#6,#9);
#6 = PRODUCT_DEFINITION_FORMATION('','',#7);
#7 = PRODUCT('Open CASCADE STEP translator 7.9 1', ... ,(#8));
#8 = PRODUCT_CONTEXT('',#2,'mechanical');
#9 = PRODUCT_DEFINITION_CONTEXT('part definition',#2,'design');
#10 = ADVANCED_BREP_SHAPE_REPRESENTATION('',(#11,#15),#345);
...340 geometry entities...
#350 = PRODUCT_RELATED_PRODUCT_CATEGORY('part',$,(#7));
----
<1> the bridge -- `SHAPE_DEFINITION_REPRESENTATION` links a
`PRODUCT_DEFINITION_SHAPE` to the `representation` carrying the actual B-Rep.

The coupling this wave builds already exists physically -- with a
placeholder product structure OCCT invented (`id`s like `'design'`, names
like `'Open CASCADE STEP translator 7.9 1'`), not the validated one
`kstep-core` builds and `dev.kstep.core.ValidationResult` checks. The real
gap is replacing that placeholder with kSTEP's own structure while keeping
OCCT's geometry.

=== The two halves are cleanly separable

Measured on real OCCT 7.9.2 output (a box and an extruded-and-filleted
solid): the transitive closure below `#10`
(`ADVANCED_BREP_SHAPE_REPRESENTATION`) is 340 instances; the remaining 10
(`#1`-`#9`, `#350`) are exactly the product structure plus the two bridge
entities. **No geometry entity references the product structure.** (Trap:
a naive `#(\d+)` regex over the raw text gives a false positive here --
`#345`'s `REPRESENTATION_CONTEXT` argument contains the literal string
`'Context #1'`. Every reference computation in this wave goes through the
tokenizer, never through text search -- see `Ap242GeometryExtractionTest`'s
dedicated case for this.)

=== The existing Part-21 reader cannot read this file at all

`Part21Tokenizer` (pre-Welle-4) recognized exactly four value shapes
(`'string'`, `#N`, `(list)`, `$`) and threw on any unrecognized entity name.
Real OCCT output contains:

[cols="2,3,1", options="header"]
|===
| Construct | Example | Frequency in box.step

| Integer | `GEOMETRIC_REPRESENTATION_CONTEXT(3)` | present
| Real | `(0.,0.,40.)`, `1.E-07`, `-4.440892098501E-16` | pervasive
| Enumeration | `.T.` `.PCURVE_S1.` `.MILLI.` `.METRE.` `.UNSPECIFIED.` | pervasive
| Derived-attribute token `*` | `ORIENTED_EDGE('',*,*,#21,.F.)` | pervasive
| Typed parameter | `LENGTH_MEASURE(1.E-07)` | present
| Complex instance | `#345 = ( GEOMETRIC_REPRESENTATION_CONTEXT(3) ... );` | 28 in one box
| Unknown entity name | 19 of 29 distinct names in box.step | pervasive
|===

So the acceptance criterion "re-import the merged file through kSTEP's own
reader" is unreachable without extending `kstep-step21`'s value grammar --
that extension is mandatory scope, not an optional nicety.

=== DoS-guard measurements (why nothing needs loosening)

[cols="2,2,2", options="header"]
|===
| File | Instances | Bytes

| box.step | 350 | 15,451
| extruded-filleted.step | 594 | 26,902
| extruded-rectangle.step | 350 | 15,490
|===

Max reference-chain/topological-sort depth measured 15 in every fixture.
`MAX_INSTANCES = 10_000`, `MAX_SOURCE_LENGTH = 5_000_000`,
`MAX_REFERENCE_CHAIN_DEPTH = 64`, `MAX_VALUE_NESTING_DEPTH = 32` all keep
comfortable (>= 4x) headroom over these real artifacts and are left
unchanged -- see Security below for the guards this wave *does* add.

== Decision

=== Part-21-level merge, not `STEPCAFControl_Writer`/XCAF

`STEPCAFControl_Writer` would still let OCCT generate the product structure
via its own XCAF label/attribute API -- which cannot express
`product_definition_formation.id`, `product_context`/
`product_definition_context`, or, critically, run `kstep-core`'s own
`ValidationResult`/WHERE-rule checks. Coupling to `kstep-core` would be
cosmetic, not real. A Part-21-level merge -- read OCCT's raw output, keep
only the geometry subgraph, splice in kSTEP's own already-validated
instances -- is the only option where the product structure in the final
file is the one kSTEP actually validated.

=== New module `kstep-shape`, no new edge in the existing module graph

....
kstep-express --api--> kstep-core --impl--> kstep-step21
                                                 |
kstep-geometry (0 project dependencies)         |
      |                                         |
      +-----------+        +-------api----------+
                  v        v
               kstep-shape  (NEW)
....

`kstep-geometry` staying dependency-free (ADR-0005) and `kstep-core` not
gaining a dependency on it (which would drag the native `.so`-loading
machinery into `kstep-cli`/`kstep-mcp`/`kstep-script`, none of which touch
geometry) rules out adding this coupling to either existing module. The
value-grammar/document-algebra extension below lives in `kstep-step21`
itself and needs no new dependency (it operates on text/raw documents, not
geometry); the only place an `OcctShape` and a `ProductDefinition` appear
together is the new module.

=== `kstep-step21`: full value grammar + `Part21ReadMode`

`Part21Value` grows four variants (`Num`, `Enumeration`, `Derived`, `Typed`)
alongside the pre-existing `Str`/`Ref`/`ListValue`/`Unset`; `Part21EntityInstance`
(replacing the pre-Welle-4 `internal Part21RawInstance`) is `Part21SimpleInstance`
or `Part21ComplexInstance`. A new `Part21ReadMode` controls tolerance:

* `STRICT` (default, unchanged behavior) -- every entity must be a known
  `Part21EntityKind`, no complex instances, values limited to the pre-Welle-4
  four shapes. Every pre-existing caller keeps its exact prior behavior.
* `TOLERANT` -- unknown entity names and complex instances are kept
  **verbatim as opaque instances** (`Part21ReadResult.opaque`) instead of
  throwing. *Known* entities stay exactly as strict as `STRICT` in both
  modes -- a malformed `PRODUCT_DEFINITION` is never silently downgraded to
  opaque, because kSTEP controls the writer of the files this mode reads.

`Part21Value.Num` holds its lexeme **verbatim**, never parsed to `Double`:
`1.E-07` through `Double.toString()` becomes `1.0E-7`; `2013` (an INTEGER)
through `Double` becomes `2013.0`, a different Part-21 literal shape; and
`-4.440892098501E-16` is not guaranteed to round-trip bit-identically. This
wave re-emits geometry it does not own the precision of.

An opaque instance is deliberately **neither a success nor a failure** in
`Part21ReadResult` -- it appears in `opaque`, never in `instances`,
`violations`, or `skipped`. A known instance that happens to reference an
opaque one (never true of kSTEP's own merged output, but true in general of
tolerantly-read foreign files) is therefore never wrongly reported as
`skipped`.

=== `kstep-step21`: one renderer, a `Part21Document` algebra

`Part21Renderer` becomes the single text-serialization path; `Part21Writer.write`
is now `emit` (graph walk + numbering, no text) followed by
`Part21Renderer.render` -- verified byte-identical to the pre-refactor output
via the existing `Part21WriterTest` exact-string assertions, unchanged.
`Part21Document` adds `renumbered(offset)` and `Part21Document.concat(...)`,
the two operations `kstep-shape`'s merge composes.

=== `kstep-shape`: `ShapeAssignment` + `Ap242ShapeExporter`

One `ProductDefinition` to one `OcctShape` (`ShapeAssignment`, deliberately
1:1 this wave). `Ap242ShapeExporter.export`:

. Write the `OcctShape` to a real temp file via `writeStepFile`, read it back as text, delete the temp dir.
. Parse it with `Part21Reader.readRawDocument(text, TOLERANT)`.
. `Ap242GeometryExtraction.extract` finds the (single) `SHAPE_DEFINITION_REPRESENTATION`,
  walks the closure below its `used_representation` (iterative work-stack, not native
  recursion -- same DoS discipline as `Part21GraphResolver.topologicalOrder`), and
  throws `ShapeExportException` if: there isn't exactly one `SHAPE_DEFINITION_REPRESENTATION`;
  its `used_representation` isn't an `(ADVANCED_)*SHAPE_REPRESENTATION`; the closure
  reaches any product-structure entity name (OCCT's own placeholder leaking through);
  or the closure has no `MANIFOLD_SOLID_BREP`.
. `Part21Writer.emit(listOf(productDefinition), startId = 1)` numbers kSTEP's own structure.
. The geometry closure is renumbered by `structure.nextId - 1` -- guaranteed
  disjoint from the structure's ids, since it starts strictly after them.
. Four handwritten bridge instances are appended at the next free ids:
  `PRODUCT_DEFINITION_SHAPE`, `SHAPE_DEFINITION_REPRESENTATION`,
  `APPLICATION_PROTOCOL_DEFINITION`, `PRODUCT_RELATED_PRODUCT_CATEGORY` --
  handwritten, not codegen-typed, because typing them needs SELECT-type
  support `dev.kstep.express.codegen.TypeMapping` does not have (V1 limit;
  Folge-Welle 4d).
. `structure.instances + geometryRenumbered + bridge`, rendered as one `Part21Document`.

Verified end-to-end against real OCCT 7.9.2 (`Ap242ShapeExportRoundtripTest`,
OCCT-gated): export, re-import with `Part21Reader.read(text, TOLERANT)`,
`isFullySuccessful == true`, exactly one typed `ProductDefinition` in
`instances` matching the one kSTEP built, zero opaque `PRODUCT`/
`PRODUCT_DEFINITION` instances, the text does not contain
`"Open CASCADE STEP translator"`, and the actual *link*
(`SHAPE_DEFINITION_REPRESENTATION` -> `PRODUCT_DEFINITION_SHAPE` -> the exact
`ProductDefinition` object; `SHAPE_DEFINITION_REPRESENTATION` -> the
`ADVANCED_BREP_SHAPE_REPRESENTATION` -> a `MANIFOLD_SOLID_BREP`) is checked
by identity, not merely "both halves are present somewhere". `ADVANCED_FACE`/
`VERTEX_POINT`/`EDGE_CURVE` counts in the re-parsed opaque geometry match
`OcctShape.topology` exactly (6/8/12 for the 20x30x40mm box fixture).

== Consequences

Explicitly *out of scope*, each named as its own Folge-Welle below: multiple
shapes/assembly geometry, any DSL/CLI/MCP surface for this export, STEP
*import* of foreign files (`STEPControl_Reader`), codegen-typed bridge
entities, and loosening the tolerant reader's known-entity strictness for
arbitrary third-party files.

`kstep-step21`'s public surface grows substantially (`Part21Value`,
`Part21EntityInstance` and its two implementations move from `internal` to
`public`) so `kstep-shape` and its tests can inspect opaque instances. This
is a real, deliberate increase in what must be held API-stable going
forward -- accepted because a narrower, purpose-built facade would be more
code with less expressive test coverage for the same guarantee.

== Security

Applying the kSTEP security checklist (CLAUDE.md):

[cols="2,4", options="header"]
|===
| Area | Assessment

| SSRF | Not applicable -- no network access, no URL handling.
| DoS | All pre-existing guards (`MAX_SOURCE_LENGTH`, `MAX_INSTANCES`,
  `MAX_VALUE_NESTING_DEPTH`, `MAX_REFERENCE_CHAIN_DEPTH`) are unchanged and
  keep >= 4x headroom over the largest real fixture measured (594
  instances/27KB/depth 15). New: `MAX_COMPLEX_INSTANCE_PARTS = 64` (measured
  max 4 in real OCCT output); `Typed`-parameter nesting counts against
  `MAX_VALUE_NESTING_DEPTH`; `Ap242GeometryExtraction`'s closure walk is
  iterative (explicit work-stack) with its own depth (`4096`) and size
  (`200_000`) caps, never native recursion.
| Cryptography | Not applicable.
| Resource leaks | `Ap242ShapeExporter` never closes the caller's `OcctShape`
  (same ownership rule as `OcctKernel.fillet`'s input shape). The temp
  directory (`Files.createTempDirectory`, owner-only permissions,
  unpredictable name -- never a fixed shared path, which would be a
  symlink/TOCTOU target) is deleted in a `finally` block regardless of
  success or failure.
| Injection across the export boundary | *The main new control.* Before this
  wave, `Part21Writer`'s `assertEncodable` only ever validated
  `kstep-core`-originated strings. From this wave on, foreign values
  (OCCT-sourced strings, and any programmatically-constructed
  `Num`/`Enumeration`/`Typed`/entity name) are re-emitted verbatim.
  `Part21Renderer` now validates **every** value it writes: `Str` through
  the existing `assertEncodable`; `Num` against the ISO 10303-21 number
  grammar; `Enumeration.name`/`Typed.keyword`/entity names against
  `[A-Za-z_][A-Za-z0-9_]*`; every instance id and `Ref` id against `> 0`,
  matching `Part21Tokenizer.parseInstanceId`'s read-side invariant --
  closing a fail-open gap where `Part21Document.renumbered`'s (unchecked
  at the time) `id + offset` arithmetic could overflow into a non-positive
  id that was written verbatim instead of rejected. `renumbered` itself
  now uses `Math.addExact` and throws `Part21WriteException` on overflow,
  as does `Ap242ShapeExporter`'s own bridge-entity id allocation
  (`nextFreeId + 1/2/3`). Without this, a value like
  `Num("1); INJECTED(")` could break out of its argument-list position.
  Covered by `Part21DocumentMergeTest`.
| Logging | `kotlin-logging` throughout (repo convention). The best-effort
  temp-directory cleanup warning (`Ap242ShapeExporter.deleteRecursively`)
  does log the temp path itself -- an unpredictable-named path under the
  JVM temp root, not a secret, but a path nonetheless. `Part21Renderer`'s
  and `OcctShape`'s exception messages echo the offending value/path, and
  `Part21Renderer`'s echoed value (a foreign string, number lexeme, or
  identifier, up to `MAX_SOURCE_LENGTH`) is truncated to 80 characters
  before being embedded. `Part21Tokenizer` carries the identical guarantee
  at the read boundary: its own `truncateForMessage` (same 80-character
  cap) bounds the two messages that echo raw parsed text (HEADER
  statement-name mismatch, unknown entity name); `parseIdentifier`
  itself additionally caps every identifier it accumulates at 128
  characters (`MAX_IDENTIFIER_LENGTH`), independent of `MAX_SOURCE_LENGTH`;
  `parseInstanceId` applies the same `truncateForMessage` cap to the
  digit run it echoes in its "not a valid integer" message (an
  unbounded-length `#<digits>` has no `MAX_IDENTIFIER_LENGTH`-style limit
  of its own, since it is numeric, not an identifier); and
  `asString`/`asStringList` -- which validate the `FILE_DESCRIPTION`/
  `FILE_NAME`/`FILE_SCHEMA` HEADER arguments in `buildHeader`, reachable
  via the public `Part21Reader` entry point in both `Part21ReadMode`s --
  describe a shape-mismatched value via the same fixed-word `describeShape`
  helper `checkArgShape` uses ('STRING', 'a NUMBER', ...) rather than
  interpolating the `Part21Value` itself, whose data-class `toString()`
  would otherwise echo the entire parsed payload up to `MAX_SOURCE_LENGTH`.
  `Part21GraphResolver.checkDangling` bounds its own message the same
  way, but along a different axis: instead of one huge echoed value, a
  file with many opaque instances that each reference one undefined `#N`
  could make its `joinToString` message grow linearly with the whole
  file, so it reports at most `MAX_DANGLING_REFERENCES_REPORTED` (20)
  pairs and appends an "and N more" summary for the rest. So a caller
  that logs a `Part21Reader`/`Part21Renderer` exception cannot have an
  unbounded amount of parsed input land in one log line. No native
  handles appear in log/exception text.
| License | No new third-party dependency; OCCT usage unchanged (system-
  installed, LGPL-2.1 + Open CASCADE Exception 1.0).
|===

== Folge-Wellen (updates to ADR-0005's table)

[cols="1,4", options="header"]
|===
| Wave | Content

| Geometrie Welle 4
| **Implemented, see this ADR.**

| Geometrie Welle 4b
| Assembly geometry: multiple `ShapeAssignment`s in one file,
  `NEXT_ASSEMBLY_USAGE_OCCURRENCE` + `CONTEXT_DEPENDENT_SHAPE_REPRESENTATION`
  + `ITEM_DEFINED_TRANSFORMATION` for component placement.

| Geometrie Welle 4c
| DSL/tooling surface: a `shape { }` block in `.kstep.kts` (`kstep-script`),
  `kstep export --with-geometry` (`kstep-cli`), an MCP tool (`kstep-mcp`).

| Geometrie Welle 4d
| Codegen-typed `product_definition_shape`/`shape_definition_representation`/
  `shape_representation` in `kstep-core` -- needs SELECT-type support in
  `dev.kstep.express.codegen.TypeMapping` and a materially larger EXPRESS
  extraction.

| Geometrie Welle 4e
| STEP *import* of foreign files (`STEPControl_Reader` in `kstep-geometry`,
  ADR-0005 Welle 2), plus loosening the tolerant reader's known-entity arity
  strictness so genuinely third-party AP242 files (not just kSTEP's own
  merged output) can be read.

| Geometrie Welle 4f
| Raise the Part-21 DoS limits (`MAX_INSTANCES`, `MAX_SOURCE_LENGTH`) once
  measured against a real part with >= 100,000 entities -- left unchanged
  this wave, since the largest real artifact measured is 594 instances.

| Geometrie Welle 4g
| Implement ISO 10303-21's `\X\`/`\X2\`/`\X4\` escapes in
  `Part21Renderer.assertEncodable`, so non-ASCII part names become possible
  (currently `Part21EncodingException`).
|===
