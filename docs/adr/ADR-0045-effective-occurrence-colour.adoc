= ADR-0045: Effective colour per occurrence in `kstep import` and instance colours in `kstep render` (Welle W)
:toc:

== Status

Accepted, implemented (kSTEP Welle W). It closes the two follow-ups that ADR-0044 left open (D7 and "Not built"): the
effective colour of one placed occurrence in `kstep import`, and instance colours in `kstep render`. No native code and no
file-format change: the STEP export of ADR-0044 is untouched.

== Decisions

D1:: *Effective colour of an occurrence (import).* Instance colour over part colour: the colour of the _last_ component on
the path (the component that points directly at the part), otherwise the whole-part colour `ImportedPart.color`, otherwise
`null`. `ImportedOccurrence` gets `color` as its last constructor parameter (default `null`).

D2:: *Colours on intermediate components are ignored.* A colour on a sub-assembly component does not reach the parts below
it; path-exact colours stay unbuilt (ADR-0044 D4). The importer's `Frame` stores the instance colour of the component that
was pushed last and never inherits it.

D3:: *Only the whole-part colour counts.* Face colours, edge colours and layers do not flow into the effective value.

D4:: *JSON and text.* `occurrences[].colour` is always present and `null` without a colour (additive, like every earlier
colour key; the document has no format version). The text report appends `  colour (r, g, b)` to the occurrence line only
when the occurrence has an effective colour, so the report of a file without colours is byte-identical.

D5:: *Instance colours in the render.* `PlacedInstance` carries the `usage` that placed it (`null` for a shaped root). The
preview maps `model.usageStyles` by object identity of the usage (NAUO ids are not guaranteed unique) and uses the instance
colour before the part colour. A usage colour belongs to a usage, not to an instance: if an assembly occurs twice and
contains the coloured leaf, both resulting instances get the colour. This is consistent with the export, where the style
is also per usage.

D6:: *No change without instance colours.* The path is chosen exactly as before: `anyColour` is true if a part has a
colour or an instance has a usage colour; otherwise `colored` stays `null` and the plain merge and projection run. If only
some instances are coloured, the others use `MeshColor.NEUTRAL` (the same rule as for part colours). SVG, PNG and GLB all
run through the merged coloured mesh, so the `COLOR_0` vertex colours of the GLB follow without further change. Alpha stays
off in the render (ADR-0042); instance colours are opaque anyway (ADR-0044 D4).

D7:: *Text card.* The text renderer (`TextCardRenderer`, `PreviewSummary`) contains no colour information, so nothing
changes there.

== Hand calculation (test oracle)

One box 10 x 20 x 30 mm (volume 6000 mm3), used twice; the second occurrence sits 50 mm to the right (x = 50); instance 1 is
red, instance 2 blue. Expected: 2 occurrences, total volume 2 x 6000 = 12000 mm3, bounding boxes offset by exactly 50 mm in x,
`occurrences[0].colour` = (1, 0, 0), `occurrences[1].colour` = (0, 0, 1); the render shows a red and a blue set of fills.
The checks live in `CliExportOcctInstanceColourIntegrationTest` (round trip) and `PreviewInstanceColourOcctTest` (render).

== Limits

* No colours on sub-assembly components, no transparency on instance colours, no layers on instances.
* No opacity in the render (ADR-0042).
* No per-face colours in the effective value.
* The text card shows no colour.
* Bounded as before: `AssemblyInstanceExpander.MAX_INSTANCES` (4096) bounds the usage map used by the render.
