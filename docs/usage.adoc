= Usage (current capability)

Parsing an EXPRESS schema and generating Kotlin `data class`es from it
works end-to-end today:

[source,kotlin]
----
import dev.kstep.express.codegen.ExpressKotlinCodeGenerator
import dev.kstep.express.semantic.ExpressSemanticModelBuilder

val schema = """
    SCHEMA example_schema;
      ENTITY product;
        id   : STRING;
        name : STRING;
      END_ENTITY;
    END_SCHEMA;
""".trimIndent()

val model = ExpressSemanticModelBuilder.build(schema)
val kotlinSource = ExpressKotlinCodeGenerator.generateFileSource(
    model.schemas.single(),
    "dev.kstep.generated.example",
)
println(kotlinSource)
// package dev.kstep.generated.example
//
// public data class Product(
//   public val id: String,
//   public val name: String,
// )
----

`ExpressParserFactory.parse` (used internally by
`ExpressSemanticModelBuilder.build`) throws `ExpressSyntaxException` on
the first syntax error instead of returning a partial tree.
`ExpressSemanticModelBuilder` throws `SemanticModelException` for a
named type that resolves to neither a known entity nor a known `TYPE`
in the same schema. `ExpressKotlinCodeGenerator` throws
`CodeGenException` for EXPRESS constructs it doesn't yet turn into
Kotlin (see xref:status.adoc#status[Status]). None of this is wired into the
CLI yet; the `generateExpressKotlin` Gradle task (see xref:building.adoc[Building])
is the one place it is wired into a Gradle task today, scoped to the
six V1 entities.

Building a `kstep-core` DSL entity runs WHERE-rule validation and
returns a structured result instead of throwing for a validation
failure:

[source,kotlin]
----
import dev.kstep.core.ValidationResult
import dev.kstep.core.ap242.applicationContext
import dev.kstep.core.ap242.product
import dev.kstep.core.ap242.productContext
import dev.kstep.core.getOrThrow

// product.frame_of_reference is a mandatory SET [1:?] OF product_context in the real
// AP242 schema (M2 Welle 10 — see docs/adr/ADR-0004-core-on-generated-types.adoc);
// kstep-core does not invent a placeholder context behind the caller's back.
val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext {
    name = "engineering"
    frameOfReference = appCtx
    disciplineType = "mechanical"
}.getOrThrow()

val result = product(id = "BRK-001") {
    name = "Bracket"
    description = "Mounting bracket"
    frameOfReference = setOf(prodCtx)
}
when (result) {
    is ValidationResult.Valid -> println(result.value)
    is ValidationResult.Invalid -> println(result.violations)
}

// An empty id violates product's WHERE rule (kstep_wr1: SELF.id <> ''):
val invalid = product(id = "") { name = "Bracket"; frameOfReference = setOf(prodCtx) }
println((invalid as ValidationResult.Invalid).violations)
// [DslViolation(code=KSTEP-W-001, entityName=product, ruleLabel=kstep_wr1,
//   expressionText=SELF.id <> '', message=WHERE rule kstep_wr1 not satisfied: SELF.id <> '')]
----

`WhereRuleValidator.validate` — the lower-level API `kstep-core`'s
builders call internally — re-parses WHERE-rule expression text and
evaluates it against a `Map<String, WhereRuleValue>`:

[source,kotlin]
----
import dev.kstep.express.validation.WhereRuleSpec
import dev.kstep.express.validation.WhereRuleValidator
import dev.kstep.express.validation.WhereRuleValue

val violations = WhereRuleValidator.validate(
    entityName = "approval",
    rules = listOf(WhereRuleSpec(label = "wr1", expressionText = "SELF.level <> ''")),
    attributeValues = mapOf("level" to WhereRuleValue.StringValue("")),
)
println(violations)
// [WhereRuleViolation(entityName=approval, ruleLabel=wr1, expressionText=SELF.level <> '', sourceLine=0)]
----

A WHERE-rule expression using a construct outside the supported subset
(`QUERY`, arithmetic, `SIZEOF()`/`USEDIN()` without the Semantic core
Welle C opt-in, ...) throws
`UnsupportedWhereExpressionException`; a genuine evaluation-time
problem (a missing attribute, a non-boolean result, an
incompatible-type comparison) throws `WhereRuleEvaluationException`.
Neither is ever silently swallowed into an empty violation list.

(M1 Welle 5) Exporting a `kstep-core` product structure to a STEP
Part 21 physical file, then reading it back:

[source,kotlin]
----
import dev.kstep.core.ap242.applicationContext
import dev.kstep.core.ap242.product
import dev.kstep.core.ap242.productContext
import dev.kstep.core.ap242.productDefinition
import dev.kstep.core.ap242.productDefinitionContext
import dev.kstep.core.ap242.productDefinitionFormation
import dev.kstep.core.getOrThrow
import dev.kstep.step21.Part21Header
import dev.kstep.step21.Part21Reader
import dev.kstep.step21.Part21Writer

val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext {
    name = "engineering"; frameOfReference = appCtx; disciplineType = "mechanical"
}.getOrThrow()
val defCtx = productDefinitionContext {
    name = "engineering"; frameOfReference = appCtx; lifeCycleStage = "design"
}.getOrThrow()

val bracket = product("BRK-001") { name = "Bracket"; frameOfReference = setOf(prodCtx) }.getOrThrow()
val builtFormation = productDefinitionFormation("BRK-001-F") { ofProduct = bracket }.getOrThrow()
val definition = productDefinition("BRK-001-D") {
    formation = builtFormation
    frameOfReference = defCtx
}.getOrThrow()

val header = Part21Header(
    fileName = "bracket.step",
    timestamp = "2026-07-19T12:00:00",
    schemaIdentifiers = listOf("AP242_MANAGED_MODEL_BASED_3D_ENGINEERING_MIM_LF"),
)
val exported = Part21Writer.write(header, listOf(definition))
println(exported)
// ISO-10303-21;
// HEADER;
// FILE_DESCRIPTION((),'2;1');
// FILE_NAME('bracket.step','2026-07-19T12:00:00',(),(),'','kSTEP','');
// FILE_SCHEMA(('AP242_MANAGED_MODEL_BASED_3D_ENGINEERING_MIM_LF'));
// ENDSEC;
// DATA;
// #1=APPLICATION_CONTEXT('config control');
// #2=PRODUCT_CONTEXT('engineering',#1,'mechanical');
// #3=PRODUCT('BRK-001','Bracket',$,(#2));
// #4=PRODUCT_DEFINITION_FORMATION('BRK-001-F',$,#3);
// #5=PRODUCT_DEFINITION_CONTEXT('engineering',#1,'design');
// #6=PRODUCT_DEFINITION('BRK-001-D',$,#4,#5);
// ENDSEC;
// END-ISO-10303-21;

val result = Part21Reader.read(exported)
println(result.isFullySuccessful) // true
----

`Part21Reader.read` throws `Part21SyntaxException`,
`Part21EncodingException`, `Part21DanglingReferenceException`,
`Part21CycleException`, or `Part21LimitExceededException` for
structurally malformed input (see xref:status.adoc#status[Status]). A
`WHERE`-rule failure while reconstructing a parsed instance is never
thrown — it surfaces in `Part21ReadResult.violations`, with any
dependent instance recorded in `Part21ReadResult.skipped` instead of
attempted:

[source,kotlin]
----
// A hand-edited file with an empty product id (violates product's kstep_wr1 WHERE rule):
val handEdited = """
    ISO-10303-21;
    HEADER;
    FILE_DESCRIPTION((),'2;1');
    FILE_NAME('n','t',(),(),'','','');
    FILE_SCHEMA(('S'));
    ENDSEC;
    DATA;
    #1=APPLICATION_CONTEXT('cc');
    #2=PRODUCT_CONTEXT('eng',#1,'mech');
    #3=PRODUCT('','x','',(#2));
    #4=PRODUCT_DEFINITION_FORMATION('PDF-001','',#3);
    ENDSEC;
    END-ISO-10303-21;
""".trimIndent()

val badResult = Part21Reader.read(handEdited)
println(badResult.violations) // {3=[DslViolation(code=KSTEP-W-001, ...)]}
println(badResult.skipped)    // {4=[3]}
----

`Part21Writer`/`Part21Reader` are called directly here as a library
API; (M2 Welle 6) below, the `kstep export` CLI subcommand wraps this
same pair via the `kstep-script` scripting DSL instead of hand-written
Kotlin.

(M2 Welle 1) Driving the `kstep-mcp` server end-to-end from an MCP
client — the same tool-call sequence an LLM agent would make, here
shown via the SDK's own in-memory `ChannelTransport` rather than a
real stdio subprocess:

[source,kotlin]
----
import dev.kstep.mcp.buildServer
import io.modelcontextprotocol.kotlin.sdk.client.Client
import io.modelcontextprotocol.kotlin.sdk.testing.ChannelTransport
import io.modelcontextprotocol.kotlin.sdk.types.Implementation

val server = buildServer() // registers all fifteen tools on a fresh EntityStore
val (clientTransport, serverTransport) = ChannelTransport.createLinkedPair()
server.createSession(serverTransport)

val client = Client(clientInfo = Implementation(name = "example-client", version = "1.0"))
client.connect(clientTransport)

// product.frame_of_reference is mandatory (M2 Welle 10) — build a context first.
client.callTool("build_application_context", mapOf("handle" to "AC", "application" to "cc"))
client.callTool(
    "build_product_context",
    mapOf("handle" to "PC", "name" to "eng", "frame_of_reference_handle" to "AC", "discipline_type" to "mech"),
)

val built = client.callTool(
    "build_product",
    mapOf("id" to "BRK-001", "name" to "Bracket", "frame_of_reference_handles" to listOf("PC")),
)
println(built.structuredContent)
// {"id":"BRK-001","name":"Bracket","description":null,"frame_of_reference_handles":["PC"],"entityType":"product"}

// A validation failure comes back as structured content, not a protocol-level error.
// Both the empty id (WHERE rule) and the never-set name (mandatory attribute, (M2 Welle 7))
// are collected in the same response, not just the first one found:
val invalid = client.callTool(
    "build_product",
    mapOf("id" to "", "frame_of_reference_handles" to listOf("PC")),
)
println(invalid.isError) // true
println(invalid.structuredContent)
// {"errorKind":"validation_failed","violations":[
//   {"code":"KSTEP-W-001","entityName":"product", ...},
//   {"code":"KSTEP-M-002","entityName":"product","message":"required attribute 'name' ..."}
// ]}
----

To run the server for real, `kstep-cli` wraps this directly (M2 Welle 3):

[source,shell]
----
kstep mcp
----

This blocks on stdin/stdout until the session closes, exactly like
`runStdioServer()` above — `kstep mcp` is a one-line call to it, nothing
more. In practice, expect the process to be terminated by its MCP host
(SIGTERM/SIGKILL) rather than to exit on its own from a clean stdin
close: an immediate stdin EOF does not reliably make `runStdioServer()`
return in the underlying `kotlin-sdk-server:0.14.0` transport, a
pre-existing SDK behavior out of scope for `kstep-cli` to work around
(see xref:status.adoc#status[Status]). Once `runStdioServer()` does return —
whichever way the session actually closes — the process exits on its own
with code `0`; no explicit shutdown call is needed on that path.

(M2 Welle 4) Evaluating a `DERIVE` initializer expression works exactly
like `WhereRuleValidator.validate` above, via `DerivedAttributeEvaluator`:

[source,kotlin]
----
import dev.kstep.express.validation.DerivedAttributeEvaluator
import dev.kstep.express.validation.WhereRuleValue

val value = DerivedAttributeEvaluator.evaluate(
    expressionText = "SELF.id",
    attributeValues = mapOf("id" to WhereRuleValue.StringValue("W-1")),
)
println(value) // StringValue(value=W-1)

// The real AP242 product_definition.name DERIVE (get_name_value(SELF)) is a function
// call, outside the supported subset — this throws, exactly like an equivalent WHERE
// rule would:
// DerivedAttributeEvaluator.evaluate("get_name_value(SELF)", emptyMap())
// -> UnsupportedWhereExpressionException
----

(Semantic core Welle B) Within the supported subset, the code generator
turns a `DERIVE` into a computed property instead (ADR-0021). For

[source]
----
ENTITY shape_info;
  count : INTEGER;
  note  : OPTIONAL STRING;
DERIVE
  is_big   : BOOLEAN := count > 10;
  has_note : BOOLEAN := EXISTS(note);
END_ENTITY;
----

the generated class is

[source,kotlin]
----
public data class ShapeInfo(
  public val count: Int,
  public val note: String? = null,
) {
  public val isBig: Boolean
    get() = ((count).toDouble().compareTo((10).toDouble()) > 0)

  public val hasNote: Boolean
    get() = (note != null)
}
----

The derived values are not constructor parameters and not part of
`equals`/`hashCode`/`copy`/`toString`. `ExpressKotlinCodeGenerator.generateFileWithReport`
additionally returns the DERIVEs it had to skip when
`derivedAttributeMode = GENERATE_SUPPORTED_REPORT_UNSUPPORTED` is set.

`build_next_assembly_usage_occurrence` now also enforces NAUO's real
`UNIQUE UR1` rule — a second NAUO sharing an already-used
`(reference_designator, relating_product_definition)` pair is rejected:

[source,kotlin]
----
// after building NAUO-1 with reference_designator "RD-1" and
// relating_product_definition_id "PD-A":
val conflict = client.callTool(
    "build_next_assembly_usage_occurrence",
    mapOf(
        "id" to "NAUO-2",
        "relating_product_definition_id" to "PD-A",
        "related_product_definition_id" to "PD-OTHER",
        "reference_designator" to "RD-1",
    ),
)
println(conflict.isError) // true
println(conflict.structuredContent)
// {"errorKind":"unique_constraint_violated","entityType":"next_assembly_usage_occurrence",
//  "ruleLabel":"UR1","conflictingId":"NAUO-1","fields":[...]}
----

By contrast, `build_product_definition_formation` deliberately has **no**
such `UNIQUE` check — and needs none. Its real `UR1` is `(id, of_product)`,
and because the `EntityStore` already keys every formation by `id`, two
formations can only share a composite key by sharing `id`, which is a
re-build (overwrite), not a second instance. Two formations of the *same*
product under *different* ids both succeed (a product legitimately has
many formations); re-building under the same id overwrites. No
`unique_constraint_violated` is reachable for this entity — verified by
test, not just asserted:

[source,kotlin]
----
// after building product "SHARED-PRODUCT":
val first = client.callTool(
    "build_product_definition_formation",
    mapOf("id" to "PDF-A", "of_product_id" to "SHARED-PRODUCT"),
)
val second = client.callTool(
    "build_product_definition_formation",
    mapOf("id" to "PDF-B", "of_product_id" to "SHARED-PRODUCT"),
)
println(first.isError)  // null — different id, so (id, of_product) cannot collide
println(second.isError) // null — same story, even though of_product is shared

// rebuilding PDF-A under the SAME id overwrites, it does not conflict:
val rebuilt = client.callTool(
    "build_product_definition_formation",
    mapOf("id" to "PDF-A", "of_product_id" to "SHARED-PRODUCT"),
)
println(rebuilt.isError) // null
----

(M2 Welle 6) Exporting a `*.kstep.kts` script directly to a STEP Part 21
file via `kstep export`, no hand-written Kotlin caller needed. A script
ends with `stepFile(fileName = "...") { ... }`; the sixteen `kstep-core`
builders (twelve at M2 Welle 10, four more since ADR-0023), the generated `dev.kstep.generated.ap242v1.*`
types, and `stepFile`/`root` are all available without any `import`
(`KStepScriptCompilationConfiguration`'s `defaultImports`):

[source,kotlin]
----
// bracket.kstep.kts
val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext {
    name = "engineering"; frameOfReference = appCtx; disciplineType = "mechanical"
}.getOrThrow()
val defCtx = productDefinitionContext {
    name = "engineering"; frameOfReference = appCtx; lifeCycleStage = "design"
}.getOrThrow()

val bracket = product("BRK-001") { name = "Bracket"; frameOfReference = setOf(prodCtx) }.getOrThrow()
val bracketFormation = productDefinitionFormation("BRK-001-F") { ofProduct = bracket }.getOrThrow()
val definition = productDefinition("BRK-001-D") {
    formation = bracketFormation
    frameOfReference = defCtx
}.getOrThrow()

stepFile(fileName = "bracket.step") {
    root(definition)
}
----

[source,shell]
----
kstep export bracket.kstep.kts
# Exported 1 root(s) to bracket.step
----

`--validate` additionally runs the population-level model validation
(`USEDIN`/`INVERSE`/`UNIQUE` rules and the acyclic usage check, ADR-0024)
before anything is written. It is off by default. On findings the command
exits with status 1 and writes no file; if no verdict can be reached (a
limit is exceeded, a schema construct is unsupported) it fails closed with
`KSTEP-S-005`. Only `root(...)` entities are validated, not `shape(...)`.

*Declared targets (ADR-0065).* A script can name its export files in an `export { }` block inside `stepFile`
(ADR-0063): `export { step("bracket.step"); stl("bracket.stl") }`. `kstep export` writes them when asked:

[source,shell]
----
kstep export bracket.kstep.kts --target step                 # one declared target, by format id
kstep export bracket.kstep.kts --target stl --tolerance 0.05 # a mesh target, absolute chordal deviation in mm
kstep export bracket.kstep.kts --all-targets --out-dir out   # every declared target into an existing folder
kstep export bracket.kstep.kts --all-targets --force --output json
----

`--target` takes a format id (`step`, `glb`, `stl`, `3mf`) or an exact declared file name, is repeatable (at most four)
and cannot be combined with `--all-targets` or `--out`. `--out-dir` must exist (it is never created; default: the folder
of the script). An existing file stops the run (exit 1, nothing written) unless `--force` is given; a link, a directory or
the script itself is never replaced. Everything is checked and produced before the first file is written, and each file
is written atomically (a failure part-way keeps the earlier files and lists them). GLB, STL and 3MF need geometry and the
native bridge; without them the whole run fails with `geometry_unavailable` and writes nothing, not even the STEP file.
`--tolerance` applies to STL and 3MF targets only. `--validate` and `--require-geometry` work as for a plain export.
Without `--target` or `--all-targets` the command behaves exactly as described above, whether or not the script declares
targets. The success document (one line):

[source,json]
----
{"status":"success","command":"export","outDir":"/work/out","rootCount":1,"shapeCount":0,
 "targets":[{"format":"step","fileName":"bracket.step","outPath":"/work/out/bracket.step","byteLength":2214,"replaced":false}]}
----

Errors carry `"command":"export"` and an `errorKind` such as `no_export_targets`, `export_target_not_declared`,
`export_target_invalid`, `target_exists`, `out_dir_invalid` or `geometry_unavailable`.

*Geometry (ADR-0027).* A script that registers `shape(definition, occtShape)`
(together with `root(...)` for the same product structure) is exported with its
B-Rep geometry merged into the one Part 21 file, linked to the product
definition via `PRODUCT_DEFINITION_SHAPE` and `SHAPE_DEFINITION_REPRESENTATION`.
Several shapes are allowed (one per product definition, each reachable from the
roots); this section describes the unplaced case (ADR-0027): without `place(...)` every
part stays in its own coordinate system and parts overlap at the origin; placed assemblies are
covered by ADR-0028 and the `place(...)` description above. `--require-geometry` fails with
exit 1 and writes nothing unless geometry was merged (`KSTEP-S-006`: the script
registers no shape; `KSTEP-S-007`: OCCT unavailable). A failed merge
(`KSTEP-S-008`: unreachable or duplicate product definition, closed shape, OCCT
error) is never downgraded silently to a structure-only file: exit 1, nothing
written. A script that needs OCCT to build its shapes still fails during the
script run when OCCT is missing (exit 1, `KSTEP-S-003`), as before. With
geometry merged, `FILE_SCHEMA` carries OCCT's AP242 MIM identifier instead of the
structure-only identifier. `--output json` gains a `geometry` object
(`merged`, `shapeCount`, `occt`) only when shapes or the flag are involved;
otherwise the output is byte-identical to before.
Interop (2026-10-22): FreeCAD 1.1.4 reads the exported box as one valid `Solid`;
for an assembly without placements it imported only the root product (historical, ADR-0027);
since ADR-0028 FreeCAD shows the whole hierarchy with correct positions for placed assemblies.
Example for a usage cycle (A uses B, B uses A):

[source,shell]
----
kstep export cycle.kstep.kts --validate
# Model validation failed: 2 instance(s) violate population-level constraints:
#   [KSTEP-W-002] next_assembly_usage_occurrence (WR1): ... cycle path ...
# Checked 9 instance(s); indeterminate: 0; suppressed: 0; assumptions applied: 0
# Nothing was written.
----

With `--output json` the failure is `{"status":"error","errorKind":"model_validation_failed",
"command":"export","instanceCount":...,"findings":[{"entityType":...,"violations":[{"code":...,
"ruleLabel":...,"expressionText":...,"message":...}]}],...}`; an unavailable verdict is
`"errorKind":"model_validation_unavailable"` with `"code":"KSTEP-S-005"` and a `reason`. A passing
run adds a `validation` object (`performed`, `valid`, counts) to the success document. Without
the flag the output is unchanged.

`--out` overrides the derived output path; `--output json` renders the
same information as a JSON document instead of human-readable text —
useful for tool/LLM consumption (kSTEP-ADR-0001 acceptance criterion
#3). The two `root(...)` forms differ in what happens to a validation
failure: `root(entity)` takes an already-`getOrThrow()`-unwrapped
entity, so an `Invalid` result aborts the script immediately; passing
the raw `ValidationResult` to `root(...)` instead *aggregates* every
violation across every registered root, which is what the second
fixture below demonstrates:

[source,kotlin]
----
// hello-invalid.kstep.kts — an empty product id violates product's kstep_wr1 WHERE rule
// (frame_of_reference is set deliberately, so this is the only violation in the response)
val prodCtx = productContext {
    name = "engineering"
    frameOfReference = applicationContext { application = "config control" }.getOrThrow()
    disciplineType = "mechanical"
}.getOrThrow()
stepFile(fileName = "hello-invalid.step") {
    root(product(id = "") { name = "Nameless"; frameOfReference = setOf(prodCtx) })
}
----

[source,shell]
----
kstep export --output json hello-invalid.kstep.kts
----

[source,json]
----
{"status":"error","errorKind":"validation_failed","violations":[
  {"code":"KSTEP-W-001","entityName":"product","ruleLabel":"wr1",
   "expressionText":"SELF.id <> ''","message":"WHERE rule wr1 not satisfied: SELF.id <> ''"}
]}
----

A Kotlin syntax error, an unresolved reference, a script whose last
expression isn't a `KStepModel`, and a plain runtime exception all
produce their own structured `KSTEP-S-xxx` error document the same way
(`compilation_error`, `no_model_produced`, `runtime_error`) — see xref:status.adoc#status[Status] for the full `KStepScriptOutcome` breakdown — never a raw Kotlin
stack trace on stdout/stderr. Both fixture scripts above are the actual
`kstep-tests` test resources (`hello-assembly.kstep.kts` is the
3-part-assembly variant of the first example), not just documentation prose —
see the `kstep-tests` row in xref:modules.adoc[Modules].

Rendering a headless SVG/PNG/text/glTF preview of a `*.kstep.kts` script
via `kstep render` (see
docs/adr/ADR-0011-headless-preview-rendering.adoc and, for `-f glb`,
docs/adr/ADR-0016-gltf-glb-export.adoc) — no window, no display server.
`shape(...)` (also available with no `import`, alongside `root(...)`)
registers geometry for the preview independently of `root(...)`:

[source,kotlin]
----
// hello-box.kstep.kts
val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext {
    name = "engineering"; frameOfReference = appCtx; disciplineType = "mechanical"
}.getOrThrow()
val defCtx = productDefinitionContext {
    name = "engineering"; frameOfReference = appCtx; lifeCycleStage = "design"
}.getOrThrow()

val part = product("BOX-001") { name = "Box"; frameOfReference = setOf(prodCtx) }.getOrThrow()
val prodFormation = productDefinitionFormation("BOX-001-F") { ofProduct = part }.getOrThrow()
val definition = productDefinition("BOX-001-D") {
    formation = prodFormation
    frameOfReference = defCtx
}.getOrThrow()

// OcctKernel/shape(...) need no import -- see defaultImports above.
val box = OcctKernel.makeBox(10.0, 20.0, 30.0)

stepFile(fileName = "hello-box.step") {
    root(definition)
    shape(definition, box)
}
----

[source,shell]
----
kstep render hello-box.kstep.kts
# Wrote hello-box.svg  -- an isometric render, since OCCT is available and the box triangulated

kstep render hello-box.kstep.kts --format png -w 1200 --height 900 -o box.png
kstep render hello-box.kstep.kts --format text --with-step

kstep render hello-box.kstep.kts -f glb -o box.glb
# Wrote box.glb -- a self-contained binary glTF 2.0 document (JSON + binary buffer in one
# file); -w/--height are ignored for this format. "-f gltf" is accepted as an alias for
# "glb" -- both write the same binary container, see ADR-0016 for why a separate plain-text
# glTF format is not offered. Open it in any glTF viewer (e.g. https://gltf-viewer.donmccurdy.com/,
# or a local `<model-viewer>` page) to inspect the model interactively.
----

Mesh export for 3D printing (docs/adr/ADR-0049-mesh-export-stl-3mf.adoc): `-f stl` writes a binary STL, `-f 3mf` a 3MF
package; both in millimetres and geometry only (`-w`/`--height` are ignored):

[source,shell]
----
kstep render hello-box.kstep.kts -f stl            # Wrote hello-box.stl
kstep render hello-box.kstep.kts -f 3mf --tolerance 0.05 --require-watertight
kstep render hello-box.kstep.kts --out box.3mf     # format from the extension
----

[cols="1,3"]
|===
| Format | Contents
| `stl` | One merged triangle soup, placements applied, no colours (a warning says how many were dropped), unit mm by convention
| `3mf` | One object per distinct part and colour (local coordinates), one build item with a transform per instance, colours as base materials (alpha carried as `#RRGGBBAA`, many slicers ignore it)
|===

`--tolerance <mm>` sets the absolute chordal deviation (default automatic; never finer than the bounding-box diagonal / 2000;
non-positive or non-finite values are refused). `--require-watertight` exits 1 without writing a file when a part mesh has open
or non-manifold edges. "Watertight" here means closed and consistently oriented after welding vertices on a 1e-6 mm grid; it is
not a proof of printability. Without the flag such a mesh is still written, with a warning and `meshExport.watertight: false`
in `--output json`. A script without geometry, or without OCCT, exits 1 and writes no file. `kstep import --render` and
`kstep asciidoc` do not accept `stl`/`3mf`.

A script with an assembly structure (`NEXT_ASSEMBLY_USAGE_OCCURRENCE` roots, with or without
`place(usage, translation, rotation)`) renders every drawn instance at its composed place: SVG, PNG and GLB
show the whole assembly, the GLB as one merged mesh (ADR-0035, `geometry.instanceCount` in `--output json`).
A model with several shapes but no assembly usage connecting them still previews only the first shape, with a
warning. The `kstep-viewer` does not load scripts, so it is not affected.

On a machine without the native OCCT bridge (or if triangulation fails
for any other reason), the SAME `hello-box.kstep.kts` script above still
renders successfully — `content` falls back to a text card explaining
why, painted into whatever container was requested (never a silently
different file type), with the fixed OCCT-dev-packages `apt-get` command
from xref:building.adoc[Building] included in the card. Pass `--require-geometry` to
turn that silent fallback into a hard failure (exit 1) instead — e.g. for
a CI step that must guarantee a real render happened. A script without
any `shape(...)` call at all (like `bracket.kstep.kts` above) renders a
product-structure summary card the same way, `content = summary`, exit 0
— `kstep render` never requires geometry to succeed.

(kstep-asciidoc wave, see docs/adr/ADR-0019-kstep-asciidoc.adoc)
Pre-rendering `kstep` preview blocks in an AsciiDoc document — the
DSL-file-per-block-macro equivalent of `kuml-dev/kUML`'s `kuml-asciidoc`
pre-processor. Three interchangeable block forms; a document can mix all
three:

[source,asciidoc]
-----
// bracket-doc.adoc

A markdown fence, no attributes:

```kstep
val appCtx = applicationContext { application = "config control" }.getOrThrow()
val prodCtx = productContext { name = "engineering"; frameOfReference = appCtx; disciplineType = "mechanical" }.getOrThrow()
val defCtx = productDefinitionContext { name = "engineering"; frameOfReference = appCtx; lifeCycleStage = "design" }.getOrThrow()
val bracket = product("BRK-001") { name = "Bracket"; frameOfReference = setOf(prodCtx) }.getOrThrow()
val bracketFormation = productDefinitionFormation("BRK-001-F") { ofProduct = bracket }.getOrThrow()
val definition = productDefinition("BRK-001-D") { formation = bracketFormation; frameOfReference = defCtx }.getOrThrow()
stepFile(fileName = "bracket.step") { root(definition) }
```

An AsciiDoc-native delimited block, with attributes:

[kstep,bracket,format=png,width=800,height=600,alt="Bracket assembly"]
----
... same script as above ...
----

A block macro pointing at an existing script file:

kstep::bracket.kstep.kts[format=svg]
-----

[source,shell]
----
kstep asciidoc --input bracket-doc.adoc --output bracket-doc.rendered.adoc
# Wrote bracket-doc.rendered.adoc (3 block(s))
# -> bracket-doc.rendered.adoc now has three `image::...[]` lines, and the
#    corresponding bracket-doc-1.svg/bracket.png/bracket-doc-3.svg files
#    (named from the INPUT document's basename, and from the second
#    block's explicit `target=bracket`) sit next to it (or under
#    `:imagesdir:`, if the document sets one).

kstep asciidoc --input-dir docs/src --output-dir docs/build --format png
# Mirrors the whole tree: every .adoc is rewritten, every other file
# (images, includes, ...) is copied unchanged. Symlinks are skipped and
# reported, never followed.
----

Only `svg`/`png` are accepted as a block's image format (`auto`/`text`/`glb`
are rejected outright — an embeddable image is the only sensible container
here); `--format` sets the document-wide default, overridable per block via
`format=`. The same Container-Regel/Pflicht-Fallback `kstep render` follows
applies here too (via the shared `kstep-preview` module) — a script whose
geometry cannot be rendered this run becomes a notice card in the requested
image format, exit 0, unless `--require-geometry` is given. A script that
fails to *compile/validate/run* is a different failure class entirely: by
default it aborts the WHOLE document (`--on-error fail`, matching a
compiler's own instinct to stop on a syntax error) — pass `--on-error card`
to instead embed an error card for that one block and keep going, useful
while iterating on a document's scripts. Under the default `fail` policy, a
document with one good block and one broken block writes NEITHER the
rewritten `.adoc` NOR any of its images — never a half-written result.

Any OTHER AsciiDoc delimited block (`----`/`....`/`====`/`****`/`____`/
`++++`/`////`) not opened by a recognized `[kstep]`/`[source,kstep]`
attribute line passes through untouched — including one that happens to
contain `kstep::path[]`-looking text, e.g. this project's own docs showing
the syntax (see `docs/adr/ADR-0019-kstep-asciidoc.adoc`'s Stolperfalle 3).
A two-line ("setext") section title underline (`Title\n-----------\n`) is
never mistaken for such a delimiter opener, even though a `-----------` run
alone is indistinguishable from one — the scanner checks the line above it
first, matching Asciidoctor's own rule (Stolperfalle 12 in the ADR).

[[colours-layers]]
== Colours and layers in the export

Since ADR-0039 a part and single faces can carry a colour and a layer in the exported STEP file. They are annotations on
the result: no shape operation, no effect on the feature history, and a script without any colour or layer is exported
byte for byte as before.

[source,kotlin]
----
stepFile(fileName = "bracket.step") {
    root(bracket)
    shape(bracket, body, colour = StepColour.rgb(1.0, 0.5, 0.0), layer = "Housing")   // the whole part
    styleFaces(bracket, Faces.atMax(Direction3.Z), colour = StepColours.BLUE, layer = "Top", expected = 1)
}
----

* `shape(pd, shape, shapeName, colour, layer)` styles the whole part. `style(pd, colour, layer)` does the same later, in
  any order. `styleFaces(pd, selector, colour, layer, expected)` styles the faces a face selector resolves to; it resolves
  right away against the shape already registered with `shape(...)` and never guesses (an empty or wrongly sized
  selection is `KSTEP-S-011` with the candidates). Because the script runs again on every rebuild, `Faces.atMax(Z)` stays
  the top face when a dimension changes.
* A part colour and a face colour can be combined. OCCT writes the face colour as an `OVER_RIDING_STYLED_ITEM` that
  overrides the part's `STYLED_ITEM` on that face (ADR-0039, section S2); `kstep import` reads both back.
  The example above is the file `kstep-tests/src/test/resources/export-docs-colours-layers.kstep.kts`
  (`bracket` is a part, `body` an `OcctKernel` shape), exported and read back by a test that also compares it with this block.
* Colours are sRGB with components in 0..1: `StepColour.rgb(r, g, b)`, `StepColour.hex("#RRGGBB")` or the small
  palette `StepColours` (`RED`, `GREEN`, `BLUE`, `ORANGE`, `YELLOW`, `GREY`, `BLACK`, `WHITE`). Since ADR-0042 a colour
  can also be translucent, see <<alpha-edge-colours>>.
* A layer name has 1 to 128 printable ASCII characters (no backslash, not blank). At most 10000 styled faces and 256
  distinct layer names per part. A part with several solids (`OcctKernel.compound`) gives every solid the part colour and
  layer.
* One colour and one layer per part and per face. A second one is an error, equal or not.

[cols="1,3"]
|===
|Code |Meaning

|`KSTEP-S-012` |Invalid colour: a component or the alpha is not a finite number in 0..1, not `#RRGGBB` or `#RRGGBBAA`, or an edge colour is transparent.
|`KSTEP-S-013` |Invalid layer name: blank, longer than 128 characters, or a character outside printable ASCII or a backslash.
|`KSTEP-S-014` |A second colour or layer for the same part or face.
|`KSTEP-S-015` |Unknown target: a style for a part without a shape, or a face index outside the shape.
|===

`kstep render` shows the part colour (SVG, PNG and GLB with a `COLOR_0` attribute; the opacity is drawn since Welle Y); face colours, edge colours, transparency and layers appear only in
the STEP file. `kstep import` reads the result back, see xref:usage-import.adoc#import-usage[Reading a STEP file back].
`scripts/interop/verify-export-colours-layers.sh` re-checks the example exports with kSTEP, OCCT and FreeCAD. See
docs/adr/ADR-0039-export-colours-and-layers.adoc.

[[alpha-edge-colours]]
=== Transparency and edge colours

Since ADR-0042 a part or face colour can be translucent, and single edges can get a colour of their own.

[source,kotlin]
----
val block = part("BLOCK", "Glass block")
val body = OcctKernel.makeBox(10.0, 20.0, 30.0)

stepFile(fileName = "glass-block.step") {
    root(block)
    shape(block, body, colour = StepColour.rgba(0.2, 0.6, 1.0, 0.4))                                 // a translucent part
    styleFaces(block, Faces.atMax(Direction3.Z), colour = StepColour.hex("#FF8000C0"), expected = 1)  // an opaque-ish top face
    styleEdges(block, Edges.atMax(Direction3.Z), StepColours.RED, expected = 4)                     // the four top edges
}
----

* `StepColour.rgba(r, g, b, a)` and `StepColour.hex("#RRGGBBAA")` carry an opacity `a` in 0..1 (`1.0` and `FF` are
  opaque, `0.0` is fully transparent). An opaque colour is written exactly as before: a script that never uses a
  translucent colour exports byte for byte as in earlier versions. In the STEP file the opacity is a
  `SURFACE_STYLE_TRANSPARENT(1 - a)` next to the colour. Transparency applies to part and face colours.
* `styleEdges(pd, selector, colour, expected)` colours the edges an edge selector resolves to (the same selectors as for
  `fillet`, resolved right away against the registered shape, `KSTEP-S-011` on an empty or wrongly sized selection). An
  edge can get one colour (`KSTEP-S-014`). Edge colours are always opaque: the STEP curve style has no transparency, so a
  translucent edge colour is `KSTEP-S-012`.
* The example above is the file `kstep-tests/src/test/resources/export-docs-alpha-edges.kstep.kts` (`part(...)` is a
  small helper that builds a part), exported and read back by a test that also compares it with this block.
* Layers on assembly instances are not supported (OCCT does not read any usage layer pattern, see docs/adr/ADR-0047-instance-layers.adoc).
* Not covered: layers on edges, edge width and line style, and showing the opacity in `kstep render`. Colours on
  assembly instances are described below. See docs/adr/ADR-0042-transparency-edge-and-instance-colours.adoc.

`scripts/interop/verify-export-alpha-edge-instance.sh` re-checks the example exports with kSTEP and OCCT, and FreeCAD
reads the files as geometry.

[[instance-colours]]
=== Instance colours

Since ADR-0044 one placed occurrence of a part (one assembly usage) can have a colour of its own, independent of the
colour of the part. This is for one part used several times, such as a screw.

[source,kotlin]
----
val box = part("BOX-001", "Box")
val first = usage("NAUO-1", assembly, box)
val second = usage("NAUO-2", assembly, box)

stepFile(fileName = "two-boxes.step") {
    roots(first, second)
    shape(box, OcctKernel.makeBox(10.0, 20.0, 30.0))
    place(second, translation = vec(50.0, 0.0, 0.0))
    styleInstance(first, StepColour.rgb(1.0, 0.0, 0.0))   // the box at the origin is red
    styleInstance(second, StepColour.rgb(0.0, 0.0, 1.0))  // the box at x = 50 is blue
    // a translucent instance colour (Welle Y): styleInstance(second, StepColour.rgba(0.0, 0.0, 1.0, 0.5))
}
----

* The colour belongs to the usage, like `place(...)`: `styleInstance(usage, colour)` needs the usage registered with
  `root(...)` and a child that has a shape of its own or shapes below it, otherwise the export fails closed (`KSTEP-S-008`,
  nothing written). The child may be a sub-assembly (ADR-0046): the colour then applies to every part below that
  occurrence. Precedence: the colour of the occurrence's own usage, then the colour of the part, then the colours of
  usages on outer sub-assemblies (innermost first). A colour belongs to the usage, so a usage inside a sub-assembly that
  occurs twice colours that part in both occurrences.
* The colour may be translucent (`StepColour.rgba(0.0, 0.0, 1.0, 0.5)`, Welle Y); an alpha that is not a finite number in 0..1 is
  `KSTEP-S-012`. An opaque colour is written exactly as before. A second colour for the same usage is `KSTEP-S-014`.
* An instance colour is written behind everything else. A script without `styleInstance` exports byte for byte as before,
  and with it the file is the same file plus a suffix.
* `kstep import` reads it back as `components[].colour` (`null` without a colour; the text report appends
  `colour (r, g, b)` to the component line). `kstep import` also reports the effective colour of
  each occurrence as `occurrences[].colour`. `kstep render` draws instance colours (they win over the part colour, alpha
  included: SVG `opacity`, PNG blending, GLB `COLOR_0` as `VEC4` with `alphaMode BLEND`; `kstep-viewer` stays opaque). See docs/adr/ADR-0045-effective-occurrence-colour.adoc.
* Verified with OCCT's own reader, `kstep import` and FreeCAD (geometry; headless FreeCAD reads no colours):
  `scripts/interop/verify-export-instance-colours.sh`. See docs/adr/ADR-0044-instance-colours.adoc.

== Converting between scripts and notes

`kstep convert <file|dir> --to okf|kts [--out <dir>] [--force] [--recursive] [--output json] [--title <text>] [--tag <tag>]...` (ADR-0060,
ADR-0061, ADR-0071) moves between `*.kstep.kts` scripts and Markdown notes with a fenced `kstep` block, as used by the Desktop knowledge
workspace. It only handles text; a script is never run.

* `--to okf` wraps `part.kstep.kts` as `part.md`: front matter with `title` and `tags: [kstep]`, a heading and one `kstep` block.
  The script may be at most 256 KiB and must not be empty.
* `--to kts` writes every non-empty `kstep` block of `part.md` as `part.kstep.kts` (one block) or `part-1.kstep.kts`,
  `part-2.kstep.kts`, ... (several). The note may be at most 1 MiB. A note with an unclosed block, a block over 256 KiB, more than
  200 blocks or no usable block is refused.
* `--out <dir>` is the target folder; it must exist and defaults to the folder of the input.
* An existing target is replaced only with `--force`. Without it nothing is written if any target exists. Links and
  non-regular files are never replaced. A single input file must not be a symbolic link.
* kts to okf to kts returns the script unchanged (a missing final line break is added). okf to kts to okf loses front matter,
  prose and other blocks.
* `--title <text>` (not with a folder) and `--tag <tag>` (repeatable; `kstep` is always the first tag, duplicates are dropped)
  set the note's front matter, only with `--to okf`. A value that starts with `--` is taken as the value. Titles may have up to 100
  and tags up to 64 characters; tags have no spaces and no leading `#`; control and bidirectional characters are refused.
* A folder converts every matching file directly in it (`*.kstep.kts` for `--to okf`, `*.md` for `--to kts`); subfolders, links
  and hidden files are skipped. In a folder, empty scripts and notes without a `kstep` block are skipped with a hint; any other
  problem in any file stops the run and nothing is written. Two sources that would write the same name (compared without regard
  to case) are refused. At most 20,000 entries, 2,000 files, 64 MiB and 2,000 targets.
* `--recursive` (folders only) also converts sub-folders, up to 8 levels deep, and mirrors them below `--out`
  (`notes/a/b.md` gives `<out>/a/b.kstep.kts`; missing sub-folders are created, `--out` itself must exist). Links are never
  followed (skipped as `symbolic_link`), folders starting with `.` and an output folder inside the input are skipped
  (`hidden_dir`, `output_dir`). Every folder must stay below the input folder. The JSON gets `"recursive":true` and a relative
  `target` per file; the bounds count over the whole tree. Folders created in the output stay if a later write fails.
* A block can be named: ```` ```kstep {name=bracket} ````. With several blocks in a note `--to kts` writes `part-bracket.kstep.kts`
  instead of `part-2.kstep.kts`; one block keeps `part.kstep.kts`. A name is 1 to 48 of `A-Z a-z 0-9 . _ -`, starts with a
  letter or digit, and is unique in the note (case does not matter). Other attributes (also Pandoc style `{.numberLines}`) are
  ignored with a warning (`warnings` in the JSON, lines on stderr); the exit code stays 0. The name is not written back by
  `--to okf`.
* `--output json` prints exactly one JSON line instead of the text. A command line that is not valid prints the usage text and exits
  1, also with `--output json`.

[source,json]
----
{"status":"success","command":"convert","target":"kts","written":[{"name":"n-2.kstep.kts","source":"n.md","block":2}],"skipped":[{"source":"n.md","reason":"empty_block","line":1}]}
{"status":"error","command":"convert","errorKind":"target_exists","code":"KSTEP-C-008","message":"n-2.kstep.kts already exists; use --force to replace it. Nothing was written."}
----

In a folder run an error also has `errors` (every failing file, at most 50, and `moreErrors`), and `written` lists files written
before a late failure. Names are shown with control and bidirectional characters escaped; no absolute path is printed.

[cols="1,3",options="header"]
|===
| Code | Meaning
| `KSTEP-C-001` | Path invalid, without a file name, missing or not resolvable
| `KSTEP-C-002` | Wrong file ending, or a folder without a matching file
| `KSTEP-C-003` | Input is a link, not a regular file, not UTF-8, or cannot be read
| `KSTEP-C-004` | Input is over its limit (256 KiB script, 1 MiB note)
| `KSTEP-C-005` | Empty script, unclosed or too large block, too many blocks, no usable block, or every file of a folder skipped
| `KSTEP-C-006` | `--title` or `--tag` refused, or `--title` with a folder
| `KSTEP-C-007` | `--out` is missing, not a folder or not valid
| `KSTEP-C-008` | A target exists and `--force` is missing (also when it appeared meanwhile)
| `KSTEP-C-009` | A target is a link, not regular, an input, has an invalid name, or two sources give the same name
| `KSTEP-C-010` | A file could not be written
| `KSTEP-C-011` | A folder limit was exceeded
| `KSTEP-C-012` | `--recursive`: a folder is deeper than 8 levels
| `KSTEP-C-013` | `--recursive`: a folder or file leads outside the input folder (or changed while it was read)
| `KSTEP-C-014` | A block attribute is malformed or the block name is not valid
| `KSTEP-C-015` | A block name is used twice in a note, or equals the number of another block
|===

Warnings (exit code stays 0): `KSTEP-C-016` unknown block attribute ignored, `KSTEP-C-017` unterminated block attribute ignored.

== Show in Script (Desktop)

In the Desktop app, *Show in Script* (inspection panel, or a double click on a leaf in the assembly tree) selects the part's name in
the editor (ADR-0068, ADR-0091). The worker reports the script line of the `shape(...)`/`place(...)` call behind each part, so the
name on that line is selected; if the name is not on that line but occurs once in the script, that occurrence is selected; otherwise
the whole call line is marked and the message "Marked the line where this part is added; its name is defined elsewhere." appears.
This works only while the editor still holds exactly the text that was run; after an edit the app falls back to searching for the
name as a literal. Only the line is known, not the column.

== Selecting several parts and the part menu (Desktop)

Select more than one part (ADR-0092):

|===
| Gesture | macOS | Windows, Linux

| Add or remove a part | Cmd+click | Ctrl+click
| Select the rows between (tree only) | Shift+click | Shift+click
| Part menu | secondary click, Ctrl+click, Menu key or Shift+F10 | secondary click, Menu key or Shift+F10
| End the selection | Escape or a click on empty space | Escape or a click on empty space
|===

At most 1000 parts can be selected; a longer selection is cut and a short message says so. In the viewer Shift stays pan, so there
is no range there. The menu offers Show in Script (one part only), Hide, Isolate (others become transparent), Show All, Copy Name(s)
and Select Children (an assembly group). An entry that cannot work now is greyed out; reach it with the arrow keys to read why.
Hide, Isolate and Show All do not change the selection. Escape closes the menu first. Copy puts one name per line on the clipboard
(control characters shown as `‹U+xxxx›`), and only when you choose it. With several parts selected the panel shows the count, the
triangles and the combined size; there is no mass.

=== The outline of the selection

Selected parts are outlined in the accent colour with a thin halo in the window colour, so they stay visible when other parts
cover them (x-ray) or when they are transparent; a hidden part has no outline (ADR-0093). Where two selected parts touch, both
outlines are drawn. A part that is only hovered is tinted, not outlined. A selection of very many triangles (more than 40 000)
or with a very ragged silhouette falls back to the tint alone: it is a limit, not an error, and nothing is shown about it.

== Reading input files from a script

A script can read files that lie next to it and have the desktop preview follow them (ADR-0080):

----
val size = readInput("size.txt").trim().toDouble()   // text of <script folder>/size.txt
val table = inputFile("table.csv")                    // absolute path, for your own reader
----

Both resolve the name against the _folder of the script_, not against the working directory (`java.io.File("x")` does the
latter, which in the desktop worker is the folder the desktop was started in). The helpers record every name; the desktop
watches exactly those files and runs the script again when one changes or disappears. Refused with `KSTEP-S-016`: an empty or
very long name, `\`, `..`, an absolute name, a symbolic link below the script folder, anything that is not a regular file,
and more than 64 different files. `KSTEP-S-017`: the file is missing (still watched, so creating it runs the script) or larger
than the limit of `readInput` (16 MiB by default).

Limits: only files read through `inputFile` and `readInput` are observed; files read through raw `java.io` or `java.nio` are
not. Inline scripts (`kstep asciidoc`, MCP) have no script folder and answer `KSTEP-S-016`; a block of a knowledge workspace
runs as a file in the desktop's session folder, where nothing lies next to it, so `readInput` fails there with `KSTEP-S-017`. A new input that changes in the instant between its read and the first poll after the run is missed until the
next change. `kstep render --output json` stays as it was: the desktop worker additionally reports `dependencies`; the public
document does not.

== Desktop live preview

`kstep-desktop` shows a `*.kstep.kts` script as a 3D shape and updates it when the file is saved (ADR-0051). It is a
Compose Desktop application of the repository, not part of the CLI zip or of the Maven Central artifacts.

----
./gradlew :kstep-desktop:run --args="/abs/path/to/part.kstep.kts"
----

On macOS arm64 it can be packaged as an app and dmg (ADR-0082; unsigned, JVM-only, not a release artefact):

----
./gradlew clean :kstep-desktop:packageDmg -Pkstep.native.exclude=true
----

The app is `kstep-desktop/build/packaging/app/kSTEP.app`, the dmg `kstep-desktop/build/packaging/dmg/kSTEP-<version>.dmg`.
It has no native geometry bridge: scripts are compiled and checked, but geometry preview, export and import need a build from
source (the window says so). An app built on your own Mac starts directly; a downloaded unsigned dmg is blocked by Gatekeeper
("Open Anyway" in System Settings > Privacy & Security, or `xattr -dr com.apple.quarantine /Applications/kSTEP.app` at your own risk).

Without an argument, press Ctrl+O (Cmd+O on macOS) or use the Open button. Geometry needs the native OCCT bridge; on a host
that builds it (Linux x86-64, macOS arm64) it is found as for the other modules. To use a bridge built elsewhere, pass it to
the run task: `-Pkstep.occt.bridge.library=/abs/path/libkstep_occt_bridge.dylib` (and `-Pkstep.planegcs.bridge.library=...`).

The script runs in a separate, supervised worker process (60 s timeout, 2 GiB heap, bounded output), never in the window's
process; a script with an endless loop or an error cannot hang or crash the window. After an error the last good shape stays
visible with a yellow badge and the time of that result; the error bar below shows the code, `line:column` and message
("+N more" lists all errors, "Copy" copies them). Files the script reads through `inputFile`/`readInput` are watched as well
(see <<Reading input files from a script>>); if the worker's list cannot be trusted, it is ignored (`KSTEP-D-037`).

[cols="1,3",options="header"]
|===
| Key | Action
| Ctrl/Cmd+O | Open a script
| Ctrl/Cmd+S | Save the script (the preview shows the saved file)
| Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z, Ctrl+Y | Undo, redo (the editor's own history)
| Enter, Tab | New line with the indentation of the line (one level deeper after `{`); four spaces
| Ctrl/Cmd+R | Run again now (the saved file)
| Shift+Ctrl/Cmd+R | Run Unsaved: preview the editor text as it is now, once (ADR-0086)
| Shift+Ctrl/Cmd+B | Banner Actions: move the keyboard focus to the buttons of the banner (Tab or arrows, Enter or Space, Escape)
| H | Reset camera and fit scale to the current shape (`H` does not hide a part; hiding is `V`)
| T | Toggle the selected part or sub-assembly transparent (not while the editor has the focus)
| V | Toggle it hidden
| I | Isolate it: it stays visible, everything else turns transparent (parts that are hidden stay hidden)
| Shift+V | Show everything again (the opacity stays)
| Space | Cycle the selected tree row: visible, transparent, hidden (only with the focus in the tree)
| Drag, Shift-drag, scroll, double-click | Orbit, pan, zoom, reset camera (as in `kstep-viewer`)
|===

[cols="1,3",options="header"]
|===
| Code | Meaning
| `KSTEP-S-001` ... | Script errors, as in `kstep render` (compilation error, no model, runtime error)
| `KSTEP-D-001` | The script ran longer than 60 s and was stopped
| `KSTEP-D-002` | The script ran out of memory (worker heap limit 2g)
| `KSTEP-D-003` | The script or its result exceeded the output bounds (16 MiB stdout, 64 MiB GLB)
| `KSTEP-D-004` | The model has more than 130 000 triangles
| `KSTEP-D-005` | The file is missing or not a `.kstep.kts` script (the window waits for it to reappear)
| `KSTEP-D-006` | The worker process could not be started
| `KSTEP-D-007` | The result could not be read (worker crash or signal, no JSON, invalid GLB)
| `KSTEP-D-008` | Geometry preview failed (triangulation or placement)
| `KSTEP-D-009` | The script is larger than 1 MiB: preview only, not editable
| `KSTEP-D-010` | The file is not editable text (NUL byte, invalid UTF-8, a line over 20 000 characters): preview only
| `KSTEP-D-011` | Saving failed (read-only file or folder, disk full, atomic replace unsupported, other I/O); the buffer is kept
| `KSTEP-D-012` | Warning: the list of drawn parts could not be trusted (bad ranges, names, colours or too many parts); the model is shown, selection is off
| `KSTEP-D-046` | Run Unsaved: the unsaved text is larger than 1 MiB; save it to preview
| `KSTEP-D-047` | Run Unsaved: the private folder for the text is not safe (link, owner or permissions changed); the run is stopped
| `KSTEP-D-048` | Run Unsaved: the text could not be written for the run
| `KSTEP-D-049` | Run Unsaved: the folder or the name of the script is not usable, or the text belongs to another file
|===

The editor (ADR-0052) sits left of the preview. Editing does not change the preview: the preview shows the saved file, except after *View > Run Unsaved* (see below), and
the status line says which one it is while there are unsaved changes (the window title carries a dot). A click on an error in the error bar moves
the caret to it. If the file changes on disk while you have unsaved changes, a banner offers Reload (the disk version becomes the
buffer, undoable) or Keep mine (the next save overwrites the disk version); Save writes nothing until you chose. A script that is
too large or not UTF-8 text stays preview-only, with the reason in the banner. Closing the window or opening another file with
unsaved changes asks Save / Don't Save / Cancel; a failed save keeps the window open.

Run Unsaved (ADR-0086): *View > Run Unsaved* (Shift+Ctrl/Cmd+R, enabled when the editor has unsaved changes) runs the editor text once,
without saving it. The script runs as if it were the real file: input files are read from its own folder. The status line shows
*Preview: unsaved buffer* (or *(older)* when you have typed since), the old picture is dimmed while the run is in progress, and the
error marks refer to the text that was run. A save, a change on disk or *Run* starts a normal run again. Export and Save always use
the saved file; the export dialog says so. A note previews only the saved file, and while a draft offer is open the entry is
disabled. Texts over 1 MiB are not run (`KSTEP-D-046`). Banner keys: *View > Banner Actions* (Shift+Ctrl/Cmd+B) puts the focus on
the first usable button of the banner (Restore, Discard, Reload, Keep mine, Open or OK); Tab or the arrow keys move, Enter or
Space press, Escape gives the focus back to the editor. Known limits: on Windows the private folder is only checked for links, type and owner, and there is no worker sandbox; after `kill -9` the
folder `kstep-desktop-unsaved-*` stays in the temp folder until the system cleans it.

Preview Unsaved Changes (ADR-0087): *View > Preview Unsaved Changes* (a check item, off by default, no key, remembered) previews the
editor text while you type, without saving. A run starts 800 ms after your last edit and at most every 2 seconds, and the last edit
always runs. Nothing runs automatically while a run of the saved file is in progress, while a draft offer is open, while the window
is not focused, with no file open, for a note (the item is disabled there), or for a text over 1 MiB (you get `KSTEP-D-046` once,
and the last good picture stays). If the script has an error, the last good picture stays and the error bar shows the error of the
text that was run; the same text is not run again. A save starts the normal run of the saved file. Export and Save still use the
saved file. Not checked by hand in a real window.

Editor comfort (ADR-0085): with the caret next to a bracket (`()`, `[]`, `{}`) and nothing selected, the bracket and its partner
are tinted; a bracket without a partner is tinted like an error line. Brackets inside strings, comments and the `${` and `}` of a
string template are ignored; a partner more than 100,000 characters away is not looked for. *View > Soft Wrap* wraps long lines at
the edge of the editor instead of scrolling sideways; the choice is remembered (off by default), the line numbers stay on the first
row of each line and the saved file is not changed. The red and yellow bars in the line-number column move with the text: a bar
stays on its line while you insert or delete lines, turns hollow when the marked text itself was edited (the error refers to the old
text) and disappears when that text is deleted. Undo does not bring a bar back; the next run replaces all bars. Files over
1,000,000 characters show no bars until the next run.

Selection (ADR-0053): moving over a part tints it, a click selects it and opens a panel at the top right of the preview with its name,
triangle count, size, centroid, colour and position. A click on empty space or Escape (while the preview has the focus) clears the
selection. A press that moves more than 4 dp is an orbit or pan, not a click. After a re-run the selection stays if a part of that name
still exists; with several parts of the same name the first one is shown.

Visibility (ADR-0055): select a part or a sub-assembly and press `T` (transparent), `V` (hidden) or `I` (isolate), or use the eye
column in the tree (a click goes visible, transparent, hidden, visible; a group whose parts differ shows a bar and becomes visible on a
click) and `Show all`, `Isolate`, `Hide` in the toolbar. The slider sets the opacity of transparent parts (5 % to 60 %). Hidden parts are
not drawn and not picked; a click picks the nearest opaque part, and a transparent one only if no opaque part is hit. A hidden part
that was selected stays selected, so its panel and tree row remain. The setting survives a re-run of the same file (parts that vanished
are dropped), is reset when you open another file, and is not saved. It is a view setting only: the script and an export do not change.
When the toolbar is too narrow the status line leaves out the least important parts (duration, triangle count first); its tooltip then shows the full text.
The status line and the tree header count the hidden and transparent parts. Known limit: parts are sorted by the depth of the middle of
each triangle, so a part inside a transparent hull can show over it when the hull has large slanted triangles; and only the front side of
a transparent hull is drawn. The colour transparency written in a STEP file is not drawn in the desktop.

Export names (ADR-0063): a script can suggest file names for the `Export...` dialog with an `export { }` block, for example
`stepFile(fileName = "bracket.step") { export { step("bracket.step"); glb("bracket-view.glb") } }`. The methods are `step`, `glb`,
`stl` and `threeMf`; at most one block, at most four names, each format once. A name must be a plain file name with the extension of
its format (`.step` or `.stp`, `.glb`, `.stl`, `.3mf`) and is rejected, not corrected, if it has a path part, a control or direction
character, a reserved Windows device name or more than 120 characters. The block writes nothing: the dialog shows the names ("From
script"), a click sets format and name, and you still choose the folder. The dialog also remembers the last format and folder
between sessions (`export.json` in the kSTEP config folder). A script without a block behaves as before.

A script without a `shape(...)` shows "Script has no shape(...)"; without the native bridge the window shows the OCCT notice
with an install hint for the current operating system.

=== Unsaved changes after a crash

While you edit, the desktop keeps a copy of the unsaved text, two seconds after your last change (at the latest 20 seconds after
the first change since the last save). The copy lives in the config folder, next to `recent.json`:

* macOS: `~/Library/Application Support/kSTEP/drafts/`
* Linux: `$XDG_CONFIG_HOME/kstep/drafts/` or `~/.config/kstep/drafts/`
* Windows: `%APPDATA%\kSTEP\drafts\`

If the app ends unexpectedly, opening the same file again shows a banner: "Unsaved changes from 14 Nov, 22:13 were found."
*Restore* puts the draft into the editor as one undo step (Undo brings back the file), *Discard* deletes it. Until you choose,
Save does nothing but make the banner flash, and nothing is written to the draft. If the file changed on disk or was deleted
since, the banner says so; saving restored text then replaces or recreates the file. A draft that equals the file is deleted
without a question. When the app starts without a file, a draft of a script that is not open is offered with *Open*.

A draft is deleted after a successful save, on Don't Save, on Discard and when you close a file without changes. It is never
written for text over 1 MiB (the old draft stays and a notice says so), at most 32 drafts are kept, and drafts older than 30 days
are removed. The files contain your text: they are readable only by you (mode 0600, folder 0700; not checked on Windows).
Limits: two instances editing the same file overwrite each other's draft (the last writer wins); after `kill -9` or a power
failure the last two to twenty seconds are lost; you can delete the `drafts` folder at any time.

=== Find and replace

The Edit menu opens the find bar, with or without the replace row. Three switches follow the field: `Aa`
matches case, `\b` matches whole words only, `.*` reads the field as a regular expression. A word is made of the ASCII letters,
digits and `_`; an umlaut or an emoji ends a word.

The regular expression is a safe subset that cannot freeze the window (ADR-0090):

[cols="1,3"]
|===
| `.`  | any character except a line break
| `[a-c]` `[^x]` `\d` `\w` `\s` `\D` `\W` `\S` | classes (`\d`, `\w`, `\s` are ASCII only)
| `^` `$` `\b` `\B` | start and end of a line, word boundaries
| `( )` `(?: )` `\|` | groups (at most 9 capturing) and alternation, the first alternative that works wins
| `*` `+` `?` `{m}` `{m,}` `{m,n}` | greedy repeats (at most 100)
|===

Back-references, look-around, lazy and possessive repeats, inline flags and named groups are refused with a message. Limits:
a pattern of 256 characters, 2,000 instructions after expansion, a file of 1 MiB, 10,000 matches. If a search needs too many
steps it stops, the counter shows "N+ matches", and Replace all is refused. An empty match right after a match is not reported.
In the replacement the dollar sign is only special with regex on: `$0` is the whole match, `$1` to `$9` the groups, `$$` a dollar
sign; a group that does not exist disables Replace. A selection copied into the field is escaped while regex is on.

=== Starting the desktop from the CLI

On macOS, with `kSTEP.app` built or installed (ADR-0082), `kstep desktop` starts the app:

[source,shell]
----
kstep desktop                       # just the app
kstep desktop part.kstep.kts        # open a script
kstep desktop notes/idea.md         # open a note (its folder becomes the workspace)
kstep desktop ~/vault               # open a folder as a workspace
----

The app is looked for in `/Applications/kSTEP.app`, then `~/Applications/kSTEP.app`; `KSTEP_DESKTOP_APP` names another app and
is then the only place that is tried (no fall back). The app must have the bundle identifier `dev.kstep.desktop`. The command
starts the app through `/usr/bin/open -n` (no shell) and returns at once; "Started" only means the start was handed over. The
path must exist, must not be a link and must be a `.kstep.kts` script, a `.md` note or a folder; a file name starting with `-` is
given as `./-x.md`. The app checks its argument again like a dropped path.

Errors (exit 1): `KSTEP-D-039` no usable app, or not macOS (on Linux and Windows start from source:
`./gradlew :kstep-desktop:run --args="<path>"`); `KSTEP-D-040` path rejected; `KSTEP-D-041` `open` failed or took longer than 30 s.

Limits: every call starts a new instance (no single instance), so two calls give two windows; the environment of your shell,
including AI key variables, is not passed on to an app started this way; an unsigned downloaded app is blocked by Gatekeeper
(ADR-0082 D7). Recent (File > Open Recent) also keeps a note that was opened on its own, with its workspace folder, but not the
notes you click in the sidebar of an open workspace.

== Native runtime archive and `kstep --version`

`kstep --version` prints `kstep <version>`. The opt-in native archive (ADR-0050, built locally with
`:kstep-cli:nativeRuntimeZip`, not part of releases) ships the OCCT and PlaneGCS bridges and a `bin/kstep` launcher; in it
`--version` also prints `occt:` and `planegcs:` status lines, and when OCCT cannot be loaded a hint is printed to stderr
(Ubuntu: `sudo apt install libocct-data-exchange-dev libocct-modeling-algorithms-dev`; macOS: `brew install opencascade`).
The archive needs OCCT 7.9.x at the location it was built against.
